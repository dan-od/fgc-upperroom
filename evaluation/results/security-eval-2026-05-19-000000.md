# Security Evaluation Report — FGC Upper Room Platform
**Date**: 2026-05-19
**Evaluator**: Claude Code (automated)
**Framework Version**: security-v1

---

## Executive Summary

**Overall Weighted Score**: 5.2 / 10
**Critical Findings**: 4 (score 1-2)
**Poor Findings**: 7 (score 3-4)

The platform has a thoughtful architecture with some strong individual controls (parameterized SQL everywhere, webhook HMAC-SHA512 verification, server-side RBAC, session invalidation on logout). However, critical gaps undermine the overall posture: all JSON data files including admin credentials and session tokens are committed to git; the main Express app and attendance service use unbounded wildcard CORS; no brute-force protection exists on the admin login endpoint; the Meta WhatsApp webhook does not verify `X-Hub-Signature-256`; and the admin token is stored in `sessionStorage` (XSS-accessible). Password hashing uses PBKDF2-SHA512 at 120,000 iterations rather than bcrypt/Argon2, which is acceptable but below modern defaults. Four of the findings are rated Critical or near-critical.

## Detailed Findings

### AUTH — Authentication & Identity

#### auth-01 Password Storage — Score: 5/10
**Evidence**: `src/api/auth.utils.ts:6-8` — `crypto.pbkdf2Sync(password, salt, 120000, 64, "sha512")`; `src/api/app.ts:59-63` — fallback plaintext password `"Admin123!"`.
**Findings**: The hashing algorithm is PBKDF2-SHA512 with 120,000 iterations and a 16-byte random salt. This is cryptographically sound but notably weaker than bcrypt cost-12 (equivalent ~2^12 = 4096 rounds of blowfish with memory-hard properties) or Argon2id. The minimum password length is only 8 characters (`admin.routes.ts:163`). Most critically, `app.ts:59-63` contains a hardcoded fallback password `"Admin123!"` that is used to seed the first admin if no environment variable is set. While this is only used at seed time, the existence of a known default credential is a serious concern, especially since the seed admin email also defaults to `admin@upperroom.local`. The seed user in `data/admin-users.json` (committed to git) was created from some prior run but with a different password than the hardcoded fallback.
**Remediation**: (1) Replace PBKDF2 with `argon2id` (via the `argon2` npm package) or at minimum bcrypt with cost 12+. (2) Remove the `"Admin123!"` fallback entirely — fail-fast at startup if `ADMIN_EMAIL` and `ADMIN_PASSWORD` are not set. (3) Enforce minimum password length of 12 characters.

#### auth-02 Session Management — Score: 5/10
**Evidence**: `src/api/admin.routes.ts:87` — `crypto.randomBytes(48).toString("hex")`; `src/api/admin.routes.ts:13` — `SESSION_DURATION_MS = 8 * 60 * 60 * 1000`; `src/api/admin.routes.ts:137-154` — server-side session deletion on logout; `src/utils/adminApi.js:8,17` — `sessionStorage.setItem(ADMIN_SESSION_TOKEN_KEY, token)`.
**Findings**: Session tokens are generated with `crypto.randomBytes(48)` (good), stored as SHA-256 hashes server-side (good), expire after 8 hours (reasonable), and are invalidated on logout (good). The critical flaw is that the raw bearer token is stored in `sessionStorage` in the browser. `sessionStorage` is accessible to any JavaScript executing in the page context, meaning an XSS attack immediately yields the admin token. Additionally, session data is persisted in `data/admin-sessions.json` which is committed to git (see secrets-04). Cookies with `HttpOnly; Secure; SameSite=Strict` would be significantly safer for a browser-based admin UI.
**Remediation**: (1) Switch from `sessionStorage` to `HttpOnly; Secure; SameSite=Strict` cookies for the admin token — this makes it inaccessible to JavaScript. (2) Remove `data/admin-sessions.json` from git tracking and add `data/` to `.gitignore`.

---

#### auth-03 MFA/TOTP — Score: 4/10
**Evidence**: `src/api/admin.routes.ts:76-84` — TOTP checked only `if (user.twoFactorEnabled && user.twoFactorSecret)`; `data/admin-users.json` — `super_admin` user `admin@upperroom.local` has `twoFactorEnabled: false`; `src/api/auth.utils.ts:64-73` — `window = 1` (±1 period = 90-second valid window).
**Findings**: TOTP infrastructure exists and works (RFC 6238 compliant using custom HMAC-SHA1 implementation, no third-party dependency). However: (1) MFA is completely optional — no role enforces it. The `super_admin` account in the committed data file has `twoFactorEnabled: false`. (2) TOTP secrets are stored in plaintext in `data/admin-users.json`. (3) No backup codes are implemented. (4) The TOTP window of ±1 period means codes are valid for 90 seconds, which is at the acceptable edge (standard is ±1). (5) No rate limiting on the OTP verification endpoint.
**Remediation**: (1) Enforce MFA requirement for the `super_admin` role — block login if `twoFactorEnabled === false` and role is `super_admin`. (2) Encrypt TOTP secrets at rest using a key from an environment variable (AES-256-GCM). (3) Implement backup codes (8+ single-use tokens). (4) Rate-limit OTP verification attempts.

#### auth-04 Brute Force Protection — Score: 2/10
**Evidence**: `src/api/admin.routes.ts:56-126` — `POST /api/admin/auth/login` handler has no rate limiting, no lockout, no delay, no failure counter.
**Findings**: The admin login endpoint (`/api/admin/auth/login`) has zero brute-force protection. There is no rate limiting, no account lockout after N failures, no CAPTCHA, no exponential back-off, and no failure logging per IP. An attacker can attempt unlimited password guesses. The only endpoint with rate limiting in the whole project is `POST /api/giving/initialize` which has a custom in-memory rate limiter at 10 requests/minute per IP. The password reset confirm endpoint (`/auth/password-reset/confirm`) is similarly unprotected. This is a Critical finding.
**Remediation**: (1) Apply `express-rate-limit` to `/api/admin/auth/login` (e.g. 5 attempts per 15-minute window per IP). (2) Implement account lockout after 10 failed attempts with a configurable lock duration. (3) Log failed login attempts with IP and email to the audit log. (4) Apply the same rate limiting to `/auth/password-reset/confirm`.

### AUTHZ — Authorization

#### authz-01 RBAC Enforcement — Score: 7/10
**Evidence**: `src/api/auth.middleware.ts:48-60` — `requireAdminPermission(permission)` middleware; `src/shared/admin-permissions.ts` — permission matrix; all admin routes use `requireAdminPermission(...)` or `requireAdminAuth` middleware at the route level.
**Findings**: RBAC is middleware-based (not handler-based), uses a well-structured permission matrix with three roles (`super_admin`, `editor`, `reviewer`), and defaults to deny. The permission check is done server-side before any handler logic. `super_admin` has wildcard permission `*`. The `requireBlogMutationAccess` custom middleware at `admin.routes.ts:21` also uses the permission module correctly. Minor concern: `POST /api/admin/audit-log` (line 463) uses `requireAdminAuth` only (any logged-in user), not `requireAdminPermission("audit:write")`, allowing any admin to inject arbitrary audit log entries.
**Remediation**: Add an `audit:write` permission to `POST /api/admin/audit-log` and restrict it to `super_admin` only, or remove the public endpoint entirely (audit log should be written only by server-side actions).

#### authz-02 API Endpoint Protection — Score: 6/10
**Evidence**: Bot `app.js:31` — `app.use(cors())` (wildcard); bot `admin-auth.js:16-31` — `assertAdmin` checks `x-bot-admin-key`; attendance `routes/attendance.js:28-35` — `assertAdmin` checks `x-attendance-admin-key`; `bot/src/routes/giving.js:25-26` — `assertAdmin(req, res)` called on `/notify`.
**Findings**: Bot and attendance admin endpoints are protected by API key checks. The giving `/notify` endpoint correctly requires `x-bot-admin-key`. Public endpoints (checkin, webhook verify) appear appropriately public. The concern is that bot and attendance apps use wildcard CORS (`cors()` with no options), meaning any origin can make authenticated cross-origin requests to these services — but since they rely on header-based API keys and are internal services, the practical risk is limited. The main website API has no global CORS middleware (giving routes have their own controlled CORS). However the attendance service (`attendance/app.js:14`) also uses `app.use(cors())` with no origin restriction.
**Remediation**: Configure CORS on bot and attendance services to explicitly list allowed origins rather than using the no-argument wildcard `cors()`.

#### authz-03 IDOR — Score: 7/10
**Evidence**: `src/api/giving-admin.routes.ts:103-159` — queries scoped by optional filters but not user-scoped (admin sees all); giving references use custom format `URG-<random>` from `lib/giving-utils.js`; `data/admin-users.json` — UUIDs used for user IDs.

UUIDs are used for all primary keys (`crypto.randomUUID()`). Payment references use a custom opaque format. The giving admin endpoint exposes donor phone/email to non-super_admin roles without masking (wait — line 145 in `giving-admin.routes.ts` DOES mask: `isSuperAdmin ? email : maskEmail(email)`) — so role-based data masking is implemented. Good finding.

### SECRETS — Secrets Management

#### secrets-01 No Hardcoded Secrets — Score: 3/10
**Evidence**: `src/api/app.ts:62` — `"Admin123!"` hardcoded fallback; `bot/src/lib/admin-auth.js:12` — `process.env.BOT_ADMIN_API_KEY || process.env.VITE_ADMIN_PASSWORD || ''`; `data/admin-users.json` committed to git with password hashes; `data/admin-sessions.json` committed (empty but tracked); `OPERATIONS.md:138` — example curl with `"password":"ChangeMe1234"`.
**Findings**: The hardcoded `"Admin123!"` default password in `app.ts:62` is a clear hardcoded secret. The fallback to `process.env.VITE_ADMIN_PASSWORD` in `admin-auth.js:12` is extremely concerning — `VITE_` prefixed env vars are embedded into the Vite client bundle and sent to every browser visitor. If a user sets `VITE_ADMIN_PASSWORD` thinking it will be used as the bot admin key, it will also be exposed in the frontend JavaScript bundle. The Paystack secret key (`PAYSTACK_SECRET_KEY`) is correctly server-side only with no `VITE_` equivalent. The `VITE_PAYSTACK_PUBLIC_KEY` exposure is acceptable (Paystack public keys are designed to be public). However, see secrets-04 for the git commit issue.
**Remediation**: (1) Remove `"Admin123!"` fallback — crash on missing env var. (2) Remove `|| process.env.VITE_ADMIN_PASSWORD` from `admin-auth.js:12` entirely. (3) Add a startup check that rejects any `BOT_ADMIN_API_KEY` that matches weak patterns (the `isWeakSecret` function exists but the check passes silently — it should block startup).

#### secrets-02 Environment Separation — Score: 5/10
**Evidence**: `env/.env.development.example`, `env/.env.production.example`, `env/.env.staging.example` — three files with dummy values; `env/` is NOT gitignored (`.gitignore` line: `!env/`).
**Findings**: Separate example files exist for development, staging, and production. The example files contain placeholder values like `replace_me_prod_*` and `pk_test_xxx...`. The `env/` directory is explicitly allowed in `.gitignore` (`!env/`), which is correct — only example files should be there. However, some placeholders in production example (`DATABASE_URL=postgresql://user:password@prod-db:5432/church_bot`) look like real credentials without the `replace_me` prefix. The `ADMIN_DEFAULT_PASSWORD=ChangeMe1234` appears in both dev and prod examples, suggesting it might be used as-is in some deployments.
**Remediation**: (1) Add validation at startup that `ADMIN_DEFAULT_PASSWORD` value is not `ChangeMe1234` in production (`NODE_ENV=production`). (2) Add similar validation for `BOT_ADMIN_API_KEY`, `ATTENDANCE_ADMIN_KEY` not matching the `replace_me_*` placeholder pattern.

#### secrets-03 Secret Rotation Readiness — Score: 4/10
**Evidence**: `OPERATIONS.md` mentions `x-bot-admin-key` usage but has no rotation runbook; session tokens are stored in `data/admin-sessions.json` which would need clearing on key rotation; no versioning of session format.
**Findings**: There is no documented process for rotating any of the secrets (Paystack keys, bot admin key, attendance admin key, META tokens, TOTP secrets). Rotating `BOT_ADMIN_API_KEY` requires updating the bot service and the main API service simultaneously (both use it). Rotating `PAYSTACK_SECRET_KEY` requires a restart. TOTP secrets cannot be rotated without disabling and re-enabling 2FA for each user. There is no evidence of secret versioning (allowing dual-key rotation without downtime).
**Remediation**: Document a rotation runbook in `OPERATIONS.md` for each secret category. Implement dual-key support for `BOT_ADMIN_API_KEY` (accept old and new key during transition period).

#### secrets-04 JSON File Store Security — Score: 1/10
**Evidence**: `git ls-files data/` output — 12 JSON files committed: `admin-users.json` (contains password hashes and salts, TOTP secrets), `admin-sessions.json`, `admin-reset-tokens.json`, `admin-audit-log.json`, `giving-transactions.json`, `contact-submissions.json`, `newsletter-subscribers.json`, `rum-events.json`, etc.; `.gitignore` has no entry for `data/`.
**Findings**: **Critical.** All 12 JSON data files including `admin-users.json` (password hashes, TOTP secrets), `admin-sessions.json` (session token hashes), `admin-reset-tokens.json` (password reset token hashes), and `giving-transactions.json` (donor PII) are committed to the git repository. Even though the hashes are not plaintext passwords, committing them means: (1) all password hashes can be cracked offline at leisure; (2) any active sessions at time of commit are exposed; (3) donor PII (names, emails, phone numbers) is in the repository history. Additionally, `writeJsonArray` in `storage.ts:57-59` uses a non-atomic `fs.writeFile` — a crash mid-write will corrupt the JSON file with no recovery mechanism (no temp-file rename pattern).
**Remediation**: (1) **Immediately** add `data/` to `.gitignore` and remove all `data/*.json` files from git history (use `git filter-repo` or BFG Repo-Cleaner). (2) Rotate all passwords and invalidate all sessions. (3) Implement atomic writes: write to `data/filename.tmp.json`, then `fs.rename` to `data/filename.json`. (4) Consider migrating sensitive admin data to the existing PostgreSQL database.

### INPUT — Input Validation

#### input-01 Server-Side Validation — Score: 6/10
**Evidence**: `src/api/giving.routes.ts:606-633` — manual validation of `donorName`, `donorEmail`, `amountKobo`; `src/api/admin.routes.ts:59-61` — email/password required check; no express-validator, Joi, or Zod in `package.json`.
**Findings**: Validation is manual (no schema library) but covers the critical fields: required field checks, email format validation, amount bounds, enum validation for roles and payment methods. Field truncation is applied (`slice(0, 120)`, `slice(0, 40)` etc.) which prevents oversized inputs. However, there is no validation on the contact form's `message` field length beyond trimming, the `phoneNumber` field in newsletter subscribe is not validated, and the RUM observability endpoint accepts arbitrary `metric`, `route`, `source` strings with no validation. No Zod/Joi/express-validator is used, which increases the risk of inconsistent validation across endpoints.
**Remediation**: (1) Add a schema validation library (Zod recommended for TypeScript). (2) Validate phone numbers in newsletter subscribe. (3) Add an allowlist for `metric` values in the RUM endpoint to prevent pollution of analytics data.

#### input-02 SQL Injection Prevention — Score: 9/10
**Evidence**: `src/api/giving.routes.ts:335-336` — `query("SELECT * FROM giving_transactions WHERE reference = $1", [reference])`; `src/api/giving-admin.routes.ts:115-116` — parameterized with dynamic `$N` placeholders; `bot/src/db/connection.js` — `query(sql, values)` pattern used throughout.
**Findings**: All SQL queries reviewed use parameterized placeholders (`$1`, `$2`, etc.) with the `pg` library. The dynamic query building in `giving-admin.routes.ts:112-117` correctly increments parameter indices when building WHERE clauses. No string concatenation SQL was found in any reviewed file. This is one of the strongest areas of the codebase.
**Remediation**: No immediate action required. Consider adding a linting rule (e.g. `eslint-plugin-no-unsafe-sql`) to enforce this going forward.

#### input-03 XSS Prevention — Score: 7/10
**Evidence**: No `dangerouslySetInnerHTML` found in any `.jsx`/`.tsx` file; `src/api/app.ts:94` — `app.disable("x-powered-by")`; no DOMPurify in `package.json`; blog/testimony content comes from admin-controlled JSON files.
**Findings**: No `dangerouslySetInnerHTML` usage was found in the React frontend. Blog and testimony content is served from admin-controlled JSON files, so XSS requires admin compromise first (acceptable trust boundary). The main XSS surface area is the admin token stored in `sessionStorage` — an XSS vulnerability anywhere in the React app would yield the admin token to an attacker. The attendance QR scan result page (`attendance/routes/attendance.js:124-146`) generates HTML by string interpolation: `${htmlMessage}` and `${result.attendeeCount || 0}` — `htmlMessage` comes from `result.message` which comes from server-side code only (not user input), so this is currently safe but fragile.
**Remediation**: (1) Add `DOMPurify` for any future rendering of user-supplied content. (2) The biggest XSS risk mitigation is switching from `sessionStorage` tokens to `HttpOnly` cookies (auth-02). (3) Escape the HTML output in the attendance scan response even though currently safe.

#### input-04 WhatsApp Message Input — Score: 6/10
**Evidence**: `bot/src/app.js:159-173` — opt-out intent check before conversation handling; `bot/src/services/inbound-conversation.service.js:6-8` — `normalizeText(messageText)`, `toLower()` applied; `bot/src/services/message-generator.service.js:131-138` — system prompt style guide provided; message text passed directly into LLM prompt.
**Findings**: Inbound message handling sanitizes input with `normalizeText` (whitespace trim) and `toLower()`. Opt-out detection runs first, preventing further processing. However, inbound WhatsApp message text is embedded directly in the LLM prompt without any escaping or injection mitigation: see `bot/src/services/message-generator.service.js:140-158` — while this is for outbound generation (not inbound), the pattern established doesn't protect against prompt injection if LLM generation were to be used for inbound conversation replies. The current inbound handler (`inbound-conversation.service.js`) does NOT use LLM — it uses keyword matching and template responses — which is the safe approach. Risk is potential future code adding LLM to inbound handling.
**Remediation**: Document explicitly that inbound WhatsApp message text must never be embedded in LLM prompts without sanitization. The current keyword-matching approach is good — retain it. If LLM is added for inbound handling, implement a sanitization step that strips special characters from user input before prompt injection.

### CRYPTO — Cryptography

#### crypto-01 HTTPS/TLS — Score: 6/10
**Evidence**: Production example `env/.env.production.example` mentions `https://bot.yourchurch.org`; Cloudflare Tunnel mentioned in `OPERATIONS.md`; no HSTS headers set in any Express app; bot `app.js:37-40` sets CSP but not HSTS.
**Findings**: The deployment appears to use Cloudflare Tunnel for HTTPS termination, which is a sound approach. However, none of the three Express applications set `Strict-Transport-Security` (HSTS) headers. If Cloudflare is bypassed (e.g. direct IP access, internal service calls, misconfiguration), connections would be plaintext. No mixed-content issues were found in the React frontend configuration.
**Remediation**: Add `res.setHeader('Strict-Transport-Security', 'max-age=31536000; includeSubDomains')` to all three apps. Verify Cloudflare "Always Use HTTPS" is enabled.

#### crypto-02 Secure Randomness — Score: 8/10
**Evidence**: `src/api/auth.utils.ts:6` — `crypto.randomBytes(16)` for salt; `src/api/admin.routes.ts:87` — `crypto.randomBytes(48)` for session token; `bot/src/services/whatsapp.service.js:219` — `Math.random()` for stub provider message ID.
**Findings**: All security-relevant randomness uses `node:crypto`. The single `Math.random()` usage is in the WhatsApp stub provider (test/development mock), not production code, so it is not a security concern.
**Remediation**: No action needed for production code. Consider adding a comment near the `Math.random()` in the stub to clarify it is intentionally non-cryptographic.

#### crypto-03 Data at Rest — Score: 4/10
**Evidence**: `bot/db/schema.sql:8-20` — `phone_number TEXT`, `email TEXT` stored in plain text in the `visitors` table; `bot/db/schema.sql:108-109` — `phone_hash TEXT` added for member_profiles (hashed); `data/admin-users.json` — password hashes committed to git; no encryption of TOTP secrets.
**Findings**: The database schema uses phone hashes (`phone_hash`) for some tables (`member_profiles`, `attendance_checkins`, `prayer_requests`, `event_rsvps`) but stores phone numbers in plaintext in the `visitors` table. Email addresses are stored in plaintext throughout. TOTP secrets in `admin-users.json` are plaintext. Donor emails and phone numbers in `giving_transactions` are plaintext. Database backup encryption is not documented. Given this is a church platform with personal data of congregation members, plaintext storage of contact details is a moderate concern under data protection regulations.
**Remediation**: (1) Encrypt TOTP secrets at rest using a server-side key. (2) Document database backup encryption procedures. (3) Consider hashing or encrypting PII in the `visitors.email` column for analytics purposes, while keeping raw data in a separate encrypted store.

### HEADERS — Security Headers

#### headers-01 Helmet.js — Score: 3/10
**Evidence**: No `helmet` in `package.json` dependencies; `src/api/app.ts` — no `helmet()` call; `bot/src/app.js:37-40` — manually sets 5 headers: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Content-Security-Policy`; `attendance/app.js` — no security headers set beyond what cors adds.
**Findings**: The bot service manually sets a good set of security headers including a restrictive CSP (`default-src 'none'`). However, the main website/API Express app (`src/api/app.ts`) sets no security headers at all beyond `x-powered-by` removal. The attendance service sets no security headers. There is no `helmet()` anywhere. The main app missing `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy`, and `Referrer-Policy` is a notable gap for an app that serves the frontend SPA.
**Remediation**: (1) Install `helmet` and add `app.use(helmet({ contentSecurityPolicy: { directives: { ... } } }))` to all three Express apps. (2) Configure CSP for the main app to restrict script sources to the CDN origin only. (3) Add headers to the attendance service.

#### headers-02 CORS — Score: 3/10
**Evidence**: `bot/src/app.js:31` — `app.use(cors())` (wildcard, no options); `attendance/app.js:14` — `app.use(cors())` (wildcard); `src/api/giving.routes.ts:521-553` — custom `givingCors` middleware with explicit origin allowlist; main `src/api/app.ts` — no CORS middleware (relies on giving routes' own CORS).
**Findings**: The bot and attendance services use unbounded wildcard CORS (`cors()` with no arguments), accepting requests from any origin. While these are internal services (typically not directly browser-facing), they are bound to `0.0.0.0` (all interfaces), and the bot serves external WhatsApp webhooks on the same Express app. A browser pointed at an internal bot URL could make cross-origin requests. The giving routes in the main app have excellent custom CORS with an explicit origin allowlist and `Vary: Origin` header. The main app otherwise has no CORS — acceptable since SPA and API are same-origin.
**Remediation**: Configure bot and attendance services with an explicit CORS origin list, e.g. `cors({ origin: ['https://fgcupperroom.org', 'http://localhost:3000'] })`.

#### headers-03 Rate Limiting — Score: 4/10
**Evidence**: `src/api/giving.routes.ts:558-582` — custom in-memory rate limiter on `/initialize` (10 req/min per IP); no rate limiting on `POST /api/contact/submit`, `POST /api/newsletter/subscribe`, `POST /api/admin/auth/login`, or any attendance endpoint.
**Findings**: Only the giving `/initialize` endpoint has rate limiting — and it's a hand-rolled in-memory implementation that doesn't survive restarts and doesn't work in multi-process deployments. All other public write endpoints (contact form, newsletter subscribe, admin login, attendance checkin) have no rate limiting. The contact form at `/api/contact/submit` accepts unlimited submissions and stores them to a JSON file (potential disk exhaustion). The newsletter subscribe endpoint has no protection against bulk subscription abuse.
**Remediation**: (1) Install `express-rate-limit` and apply across all three services. (2) Suggested tiers: admin login (5/15min), contact form (3/hour per IP), newsletter subscribe (5/hour per IP), attendance checkin (10/min per IP). (3) Replace the hand-rolled rate limiter in giving routes with `express-rate-limit`.

### ERRORS — Error Handling & Logging

#### errors-01 No Stack Traces in Responses — Score: 6/10
**Evidence**: `src/api/giving-admin.routes.ts:97-99` — `catch (err: any) { console.error(...err.message); return res.status(500).json({ error: "Failed to fetch giving summary." }) }`; `src/api/app.ts` — no global error handler middleware; `bot/src/app.js` — `try/catch` at webhook handler level.
**Findings**: Individual route handlers catch errors and return generic messages. However, there is no global error handler middleware (the `(err, req, res, next)` four-argument Express handler) in `src/api/app.ts`. If an uncaught synchronous error escapes a handler (Express 5 wraps async handlers automatically), it could result in a default Express error page that includes a stack trace in development mode. In Express 5 (which this project uses: `"express": "^5.1.0"` in `package.json`) async errors are forwarded to error middleware automatically, but without a registered error handler, Express 5 sends a generic 500. The absence of an explicit global handler is a latent risk.
**Remediation**: Add a global error handler to `src/api/app.ts`: `app.use((err, req, res, next) => { console.error(err); res.status(500).json({ error: 'An unexpected error occurred.' }); });` Place it after all routes.

#### errors-02 Secure Logging — Score: 7/10
**Evidence**: `bot/src/app.js:21-25` — `maskPhone` function used throughout; `bot/src/app.js:121` — `maskPhone(status.recipient_id)` in delivery status log; `bot/src/app.js:149` — `maskPhone(from)` in inbound message log; `bot/src/routes/giving.js:13-15,38,61` — `maskPhone` used before logging; `bot/src/lib/logger.js` — structured JSON logger.
**Findings**: Phone number masking is consistently applied in the bot layer. The giving notify endpoint logs only `reference` and `visitorId`, not full PII. Structured logging is used in the bot (via a logger module). The main website API uses basic `JSON.stringify` console logging that includes `req.originalUrl` (fine) but does not log request bodies (good). No passwords or tokens appeared in any log statement reviewed. One concern: the DB query logger in `bot/src/db/connection.js:47` logs the SQL statement text itself (`sql: statement`) — if any query happened to embed user data in the text (it shouldn't with parameterized queries), that data would be logged.
**Remediation**: Minor: consider stripping the SQL statement from the slow-query log in production, replacing with a query ID or hash.

#### errors-03 Graceful Shutdown — Score: 7/10
**Evidence**: `src/api/app.ts:163-186` — SIGTERM/SIGINT with 15s timeout, calls `server.close()`; `attendance/app.js:47-66` — SIGTERM/SIGINT with DB pool close and server close; `bot/src/index.js:50-69` — SIGTERM/SIGINT with `closeDatabase()` and server close; `bot/src/worker.js:1-3` — just starts worker, no shutdown handlers.
**Findings**: All three main services (main API, bot, attendance) have proper graceful shutdown with SIGTERM/SIGINT handlers, 15-second force-exit timeout, and service cleanup. The bot service closes the database pool. The attendance service closes the DB pool. The main API shuts down the HTTP server. However, the BullMQ worker (`bot/src/worker.js`) has no shutdown handler — it simply imports the reminder worker and logs startup. If the BullMQ worker process receives SIGTERM, it will abruptly terminate without draining in-progress jobs or closing the Redis connection. No `unhandledRejection` or `uncaughtException` handler was found in application code.
**Remediation**: (1) Add SIGTERM/SIGINT handlers to `bot/src/worker.js` that call `worker.close()` on the BullMQ Worker instance and close the Redis connection. (2) Add `process.on('unhandledRejection', ...)` to all three entry points.

### WHATSAPP — WhatsApp / Bot Security

#### wa-01 Webhook Verification — Score: 4/10
**Evidence**: `bot/src/app.js:91-103` — GET handler checks `hub.mode === 'subscribe' && token === env.META_WEBHOOK_VERIFY_TOKEN` (good); `bot/src/app.js:106-203` — POST handler has NO `X-Hub-Signature-256` HMAC verification; `env/.env.development.example:80` — `META_APP_SECRET=` (empty placeholder).
**Findings**: The Meta webhook GET verification (challenge-response) is correctly implemented. However, the POST handler that receives inbound messages and delivery statuses does NOT verify the `X-Hub-Signature-256` HMAC signature that Meta sends with every webhook. This means anyone who can reach the bot endpoint can spoof WhatsApp messages, delivery statuses, or opt-out events. A spoofed opt-out could silently unsubscribe all members. A spoofed message from a church leader's number could trigger prayer requests or feedback entries. The `META_APP_SECRET` environment variable is configured in the env config (`bot/src/config/env.js:43`) but is never used for signature verification. This is a Critical finding.
**Remediation**: Add HMAC-SHA256 signature verification to the POST webhook handler using `env.META_APP_SECRET`. The raw body must be used (before JSON parsing). Example pattern:
```javascript
const signature = req.headers['x-hub-signature-256']
const expected = 'sha256=' + crypto.createHmac('sha256', env.META_APP_SECRET).update(rawBody).digest('hex')
if (!crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expected))) {
  return res.status(403).send('Forbidden')
}
```
Note: this requires using `express.raw({ type: 'application/json' })` before the JSON middleware for the webhook route.

#### wa-02 Opt-Out & Privacy — Score: 8/10

**Findings**: Opt-out handling is one of the strongest areas. Multiple STOP keywords are recognized. Opt-out is processed before any conversation handling. The giving notification endpoint checks both `is_subscribed` and `do_not_contact` flags before sending. An `opt_outs` table persists opt-out records. A confirmation message is sent to the user. The `visitors.purge_after` and `deleted_at` columns suggest a data retention policy exists at the schema level.
**Remediation**: Minor: confirm that the opt-out confirmation message (`buildOptOutConfirmationMessage`) does not inadvertently re-engage the user (it currently does not, as the message informs them they will not receive further messages). #### wa-03 LLM Message Safety — Score: 5/10
**Evidence**: `bot/src/services/message-generator.service.js:131-138` — `BOT_MESSAGE_STYLE_GUIDE` system prompt; `bot/src/services/message-generator.service.js:395-416` — LLM output used directly as message text with no post-processing; fallback to static template if LLM returns null.
**Findings**: LLM-generated messages include a style guide prompt that instructs the model to "return only the message text" and avoid "marketing language." However: (1) LLM output is used **directly** without any content filtering, length limiting, or sanitization. A misbehaving LLM response (e.g. injection of a malicious link, inappropriate content, or excessively long message) would be sent verbatim to church members. (2) The prompts include user-supplied data (visitor name, event title) without escaping, which could allow prompt injection if an attacker controls those fields (e.g. an event title containing "Ignore previous instructions..."). (3) No output length limit is enforced (`max_tokens: 100` for OpenAI is set but not enforced post-response). (4) There is a `max_tokens: 300` for Gemini/Vertex.
**Remediation**: (1) Add output validation: trim to max 500 characters, check for URLs if not expected, fallback to template if output doesn't match expected format. (2) Sanitize user-supplied values (visitor name, event title) before embedding in prompts — strip any characters that could be interpreted as prompt directives. (3) Log LLM output before sending for audit purposes.
