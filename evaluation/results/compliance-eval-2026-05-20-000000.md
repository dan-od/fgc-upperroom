# Data Privacy & Compliance Evaluation — FGC Upper Room Platform
**Date**: 2026-05-20
**Evaluator**: Claude Code (automated)
**Framework Version**: compliance-v1
**Jurisdiction**: Nigeria (NDPR/NDPA primary; GDPR awareness for diaspora users)

---

## Executive Summary

**Overall Weighted Score**: 4.5 / 10
**Critical Findings (score 1–2)**: 3
**Poor Findings (score 3–4)**: 6

The platform has notably strong technical foundations for a church application — specifically a well-designed opt-out system, a privacy erasure API with cascading redaction, defined data retention purge logic, and phone-number masking in logs. However, these controls are severely undermined by systemic gaps that constitute real compliance risk: there is no privacy policy anywhere on the website; no consent mechanism on any public-facing form; the WhatsApp sign-up flow enrolls members without any prior disclosure of what they will receive or how their data is used; member names are sent in plaintext to three US-based LLM providers (Vertex AI/Google, OpenAI, Gemini) in cross-border transfers that are not disclosed; giving/financial donor data is exposed without masking to all admin roles (not just `super_admin`) via the legacy JSON file store route; database backups are stored unencrypted; and neither `messages` nor `conversation_feedback` table data is covered by the retention purge schedule. There is no documented data breach response plan, no DPIA process, and no published contact for data subject requests. Under NDPR, the absence of a privacy notice at the point of collection and the undisclosed cross-border transfer to LLM providers are the two most severe compliance failures.

### Key Observations
- Phone numbers are stored in **plaintext** in `visitors.phone_number`, `prayer_requests.phone_number`, `event_rsvps.phone_number`, `conversation_feedback.phone_number`, and `messages` lookup. They are also hashed in parallel columns (`phone_hash`) for indexing — but the plaintext column is always present alongside.
- **Email addresses** are stored in plaintext throughout (no hashing or encryption): `visitors.email`, `member_profiles.email`, `prayer_requests.email`, `event_rsvps.email`, `giving_transactions.donor_email`.
- **Attendance records** use only hashed or anonymized identifiers (phone_hash, ip_hash, fingerprint_hash) — better practice.
- **Message text** (full content of every WhatsApp message sent) is stored indefinitely in the `messages` table with no retention purge.

## Detailed Findings

### Consent & Lawful Basis

#### consent-01 WhatsApp Opt-In Consent — Score: 3/10

**Evidence**:
- `src/pages/Home/NewsletterModal.jsx:123` — modal title "Never Miss an Event", intro text: "Get personalized WhatsApp messages about upcoming events and weekly services."
- `src/pages/Home/NewsletterModal.jsx:127–170` — form collects name, phone, email. No checkbox for consent. No link to privacy policy. No statement of what data is stored or for how long.
- `bot/src/services/visitor.repository.js:82` — `consented_at` column is populated with `consentedAt || new Date()` — timestamp defaults to `now()` if not explicitly provided by caller.
- `bot/src/routes/visitors.js:41` — `createVisitor()` called without `consentedAt` argument from the newsletter modal submission path; the database defaults to the server timestamp, which is a server-side timestamp rather than an explicit user affirmation.
- `bot/db/schema.sql:9` — `consented_at TIMESTAMP WITH TIME ZONE` column exists in `visitors` table.
- `bot/db/schema.sql:293–296` — `welcome_message` template: "You are now on our WhatsApp list for Sunday reminders and event updates. Reply STOP any time to unsubscribe." — this is sent *after* registration, not before.
- `bot/src/services/csv-import.service.js:33–35` — CSV import validates `consented_at` must be `true/yes/1`; however, this is only for bulk admin import, not the live website sign-up flow.

**Findings**: The newsletter modal collects name, phone, and email to add the person to the WhatsApp messaging list. The `consented_at` timestamp is recorded in the database, which is good — but the *mechanism* of obtaining that consent is absent from the user interface. There is no explicit opt-in checkbox (e.g. "I agree to receive WhatsApp messages from FGC Upper Room"), no privacy notice linked from the form, and no pre-submission disclosure of what the subscriber will receive, how long data is kept, or who to contact for removal. The welcome message sent *after* registration does include opt-out instructions ("Reply STOP") and describes what will be received — but NDPR and WhatsApp Business Policy require disclosure *before* the person provides their data, not after. The CSV bulk import does enforce a `consented_at: true` check, which is a positive indication of intent, but it does not translate to the user-facing sign-up modal. Meta's WhatsApp Business Messaging Policy additionally requires explicit opt-in with clear disclosure of the business name and message category.

**Remediation**:
1. Add a consent checkbox to `NewsletterModal.jsx`: "I agree to receive WhatsApp messages about services and events from FGC Upper Room. Reply STOP any time to unsubscribe." — only enable submit button when checked.
2. Pass the checkbox confirmation timestamp as `consentedAt` in the API call so the database records explicit user consent, not just server time.
3. Add a link: "Read our privacy policy" next to the checkbox (once the privacy policy exists).
4. Audit the CSV import path: the `consented_at` gate there is good and should serve as a model for the web form.

#### consent-02 Opt-Out & Right to Withdraw — Score: 7/10

**Evidence**:
- `bot/src/services/opt-out.service.js:5` — `OPT_OUT_KEYWORDS = ['stop', 'unsubscribe', 'cancel', 'quit', 'end', 'optout', 'opt-out']` — broad keyword list.
- `bot/src/app.js:182–195` — opt-out detection runs *before* any conversation handling; immediately calls `handleOptOutRequest`.
- `bot/src/services/opt-out.service.js:32–34` — calls `updateVisitorSubscription(normalizedPhone, false)` and `markDoNotContact(normalizedPhone, reason)`.
- `bot/src/services/visitor.repository.js:238–255` — `markDoNotContact` sets `do_not_contact = true, is_subscribed = false` on `visitors` and inserts a record into `opt_outs` table — persisted in PostgreSQL.
- `bot/db/schema.sql:53–58` — `opt_outs` table with `phone_number`, `reason`, `source`, `created_at`.
- `bot/src/routes/giving.js:52–57` — `!visitor.is_subscribed || visitor.do_not_contact` checked before any giving notification message.
- `bot/src/services/opt-out.service.js:48–50` — `buildOptOutConfirmationMessage` sends "You have been successfully unsubscribed...You will no longer receive messages from us. To resubscribe, contact us directly."
- `bot/src/services/reminder.service.js` — `listSubscribedVisitors()` filters `WHERE is_subscribed = true AND do_not_contact = false AND deleted_at IS NULL` at line 128–132 of `visitor.repository.js` — reminder scheduler correctly respects opt-out.

**Findings**: The opt-out implementation is genuinely strong and is the best privacy control in the codebase. STOP and six synonyms are recognized; opt-out is processed before any message handling; both `is_subscribed` and `do_not_contact` flags are set; the `opt_outs` table provides an independent audit record; a confirmation message is sent; and all downstream paths (reminder scheduler, giving notifications) check the opt-out flags. Re-subscription requires explicit contact ("contact us directly"), not automatic re-enrolment. Minor gap: the re-subscription path (`PATCH /:phoneNumber/subscription` at `bot/src/routes/visitors.js:184`) does not verify that the subscriber is re-consenting — it is only callable by admins (via bot API key), but there is no re-opt-in consent recording when an admin re-enables a subscriber.

**Remediation**:
1. Document the re-subscription process: an admin re-enabling a subscriber should log a note (e.g. "member requested reinstatement via phone call") in the `opt_outs.reason` or an audit field.
2. Consider adding an explicit "re-subscribe" WhatsApp flow with a confirmation prompt before re-enabling.
3. Verify the event RSVP path (`bot/src/services/event-rsvp.repository.js`) also checks `do_not_contact` before sending any RSVP confirmation messages.

No link to privacy policy. `src/pages/Contact/Contact.jsx:245–249` — when subject is "prayer", a note reads: "Your request will be held in confidence. Our prayer team will lift you up." This is the only data-handling notice on any public form.

- `bot/src/services/prayer.repository.js` (via `inbound-conversation.service.js:65–71`) — prayer requests submitted via WhatsApp store `requester_name`, `requestText`, `phoneNumber` to PostgreSQL. No disclosure to the WhatsApp user that their prayer text is being stored.

**Findings**: No public-facing form on the website includes a privacy notice, consent checkbox, or link to a privacy policy. 4. For the WhatsApp prayer submission, send an acknowledgement that includes: "Your prayer request has been saved and will be seen by our pastoral team only."

### Data Minimization & Purpose Limitation

#### min-01 Collect Only What's Needed — Score: 5/10

**Evidence**:
- `bot/db/schema.sql:3–21` — `visitors` table: `name`, `email`, `phone_number`, `first_visit_date`, `consented_at`, `is_subscribed`, `do_not_contact`, `tags`, `reminder_preferences`, `timezone`, delivery failure tracking fields, `last_attendance`. All fields appear purposeful for a church messaging platform.
- `bot/db/schema.sql:99–121` — `member_profiles` table: includes `full_name`, `normalized_name`, `email`, `phone_number`, `phone_hash`, `lifecycle_state`, `lifecycle_reason`, `joined_at`, `last_seen_at`, `moved_at`, `moved_to`, `tags`, `notes`, `metadata`, `deleted_at`, `purge_after`. `notes TEXT` is an open free-text field with no defined purpose — any PII could be stored here by admins without constraint.
- `bot/db/schema.sql:123–145` — `prayer_requests`: stores `requester_name`, `email`, `phone_number`, `phone_hash`, `title`, `request_text`, `priority`, `status`, `is_confidential`, `assigned_to`, `notes`. The `email` and `phone_number` fields are stored in addition to `phone_hash`; for prayer requests, the plaintext contact details are not required for the stated purpose (prayer ministry) — the visitor can be reached via the `visitor_id` link.
- `bot/db/schema.sql:37–51` — `messages` table: stores `message_text TEXT` (full message content), `visitor_id`, `event_id`, `job_id`, `provider_message_id`, `provider_name`, `message_type`, `message_fingerprint`, `status`, `error`. Storing full message text indefinitely is likely excessive — fingerprint + status is sufficient for deduplication and delivery tracking.
- `bot/db/schema.sql:202–211` — `conversation_feedback` table: stores `phone_number TEXT` in plaintext alongside `visitor_id`. The plaintext phone number is redundant when `visitor_id` provides the link to the visitor record.
- `src/api/types.ts:51–63` — `ContactSubmission` type includes `phoneNumber` as a stored field. Phone is optional on the contact form (`Contact.jsx:215–227`), so storage is proportionate when provided — but there is no documented purpose for the phone number on a contact inquiry.
- `bot/src/services/message-generator.service.js:49–107` — `genderNameMap` maps hundreds of names to gender pronouns (m/f/n). This demographic inference table is embedded in the application code and processes name data to infer gender for personalised pronoun use. This is data derived from member names without any disclosure and could be considered unnecessary processing of a special category inference.

**Findings**: Most data collected has a clear purpose. The significant excess data items are: (1) full message text in `messages` stored indefinitely; (2) plaintext phone/email in `prayer_requests` alongside `visitor_id` link; (3) plaintext phone in `conversation_feedback`; (4) unstructured `notes` field in `member_profiles` with no content policy; (5) automated gender inference from member names without disclosure. The `genderNameMap` gender inference is a particularly subtle issue — it processes first names to categorise members by binary gender without their knowledge, which is processing additional data beyond what was collected.

**Remediation**:
1. Remove `phone_number` and `email` from `prayer_requests` — use `visitor_id` as the sole link. Migrate existing data.
2. Remove `phone_number` from `conversation_feedback` — use `visitor_id`.
3. Add a documented content policy for `member_profiles.notes` — prohibit storage of health, financial, or political information in this field.
4. Set a retention period for `messages.message_text` — consider nullifying the `message_text` column after 90 days (retain other columns for delivery tracking).
5. Remove or document the gender inference in `message-generator.service.js` — either disclose it in the privacy policy or use a gender-neutral greeting ("Hi [Name]") throughout.

#### min-02 Data Retention Policy — Score: 4/10

**Evidence**:
- `bot/src/services/privacy.repository.js:65–128` — `runRetentionPurge()` deletes:
  - `prayer_requests` with `purge_after <= now()` (30-day post-deletion schedule)
  - `event_rsvps` with `purge_after <= now()` (30-day post-deletion schedule)
  - `member_profiles` with `purge_after <= now()` (30-day post-deletion schedule)
  - `visitor_duplicates` resolved >180 days ago
  - `attendance_checkins` older than 730 days (2 years)
  - `attendance_sessions` older than 730 days with no remaining checkins
- `bot/src/services/visitor.repository.js:375–399` — `redactVisitorById` replaces PII with "Erased Member", sets `purge_after = now() + 30 days`.
- `bot/db/schema.sql:222–224` — `visitors` table has `deleted_at`, `deleted_reason`, `purge_after`, `privacy_redacted_at` columns — soft-delete and purge infrastructure exists.
- `bot/src/routes/privacy.js:63–72` — `/retention/run` endpoint exists but is manually triggered (requires `x-bot-admin-key`) — no evidence of a scheduled automatic run.
- `bot/src/scheduler/reminder.scheduler.js` — only schedules service and event reminders; no retention purge job.
- `bot/db/schema.sql:37–51` — `messages` table: no `purge_after` column, no `deleted_at`. `runRetentionPurge()` never touches this table.
- `bot/db/schema.sql:202–211` — `conversation_feedback` table: no `purge_after` column. `runRetentionPurge()` never touches this table.
- `bot/db/schema.sql:258–283` — `giving_transactions` table: no `purge_after` or `deleted_at` columns. Financial records are retained indefinitely with no stated retention period.
- `src/api/storage.ts:57–59` — JSON flat files (`contact-submissions.json`, `newsletter-subscribers.json`, `rum-events.json`, `admin-audit-log.json`): no retention purge mechanism. `contact-submissions` is capped at 5,000 records (`common.routes.ts:58`) — a data volume cap, not a time-based retention policy.
- `bot/DATA_MODEL_POLICY.md` — exists and documents data model intent (noted from `ls bot/`), but a documentation file alone does not constitute an enforceable retention schedule.

**Findings**: The retention infrastructure is partially built. Soft-delete and purge logic exists for `prayer_requests`, `event_rsvps`, `member_profiles`, and `attendance_checkins`. These represent the most sensitive personal data. However, the retention purge has three significant gaps: (1) the `messages` table (full WhatsApp message text) has no retention schedule and grows indefinitely; (2) the `conversation_feedback` table similarly has no purge; (3) the retention purge is not scheduled automatically — it must be manually triggered via API. No defined retention periods are published anywhere accessible to data subjects.

**Remediation**:
1. Add `deleted_at` and `purge_after` columns to `messages` and `conversation_feedback`. Schedule a purge of message text after 90 days.
2. Add a cron job in the BullMQ scheduler (or a separate systemd timer) to call `runRetentionPurge()` daily.
3. For `giving_transactions` — define a retention period (e.g., 7 years for financial compliance) and document it. Add `deleted_at`/`purge_after` columns for records beyond that threshold.
4. Apply time-based rotation to JSON flat files: purge `contact-submissions.json` entries older than 1 year, `rum-events.json` entries older than 90 days.
5. Document all retention periods in a Data Processing Register accessible to data subjects.

### Access to Personal Data

#### access-01 Role-Based Data Access — Score: 5/10

**Evidence**:
- `src/shared/admin-permissions.js:1–27` — Three roles defined: `super_admin` (wildcard `*`), `editor` (content and visitor read), `reviewer` (read-only content and visitor). Neither `editor` nor `reviewer` has `giving:read` in their permission list — but see below.
- `src/api/admin.routes.ts:49–74` — `GET /api/admin/giving` — `requireAdminPermission("giving:read")`. Since `giving:read` is not in the `editor` or `reviewer` permission sets, only `super_admin` can access this route. Correct.
- `src/api/giving-admin.routes.ts:93–143` — `GET /api/admin/giving/transactions` — `requireAdminPermission("giving:read")`, `isSuperAdmin` check at line 98 applies masking: `isSuperAdmin ? email : maskEmail(email)` and `isSuperAdmin ? phone : maskPhone(phone)`. Good masking for this PostgreSQL route.
- `src/api/admin.routes.ts:49–74` — **However**, the legacy `GET /api/admin/giving` route reads from the JSON flat file `data/giving-transactions.json` and returns raw records **without any masking** at lines 63–73: `data: records.slice(...)` — the raw `GivingTransaction` objects include `donorName`, `donorEmail`, `donorPhone` in plaintext. Since only `super_admin` can call this endpoint (`giving:read` is restricted), the effective PII exposure is limited — but the masking applied in `giving-admin.routes.ts` is not consistently applied in `admin.routes.ts`.
- `src/api/admin.routes.ts:76–107` — `GET /api/admin/giving/export.csv` — exports full PII (donorName, donorEmail, donorPhone) in CSV without masking, restricted to `giving:read` permission only — same super_admin restriction applies.
- `src/shared/admin-permissions.js:10–18` — `editor` role has `content:visitors:read` — this gives editors access to the full visitor list including names, phone numbers, and emails of all WhatsApp subscribers.
- `bot/src/routes/prayer-requests.js` — prayer requests in the bot API are protected by `assertAdmin` (API key check), not role-based; any caller with `BOT_ADMIN_API_KEY` can read all prayer requests regardless of pastoral role distinction.
- `src/shared/admin-permissions.js` — there is no `pastoral` role for prayer request access and no `finance` role for giving data. The `editor` role (content writing) has no business need for the full visitor list, but `content:visitors:read` grants it anyway.
- `bot/src/services/prayer.repository.js` / `bot/src/routes/prayer-requests.js` — prayer requests in the website admin dashboard are not a defined route in `src/api/admin.routes.ts` — they appear to be accessible only via the bot API with an admin key.

**Findings**: The permission model's core structure is sound (middleware-enforced, defaults to deny). The `giving:read` restriction to `super_admin` is effective for financial PII. However: (1) there is no `pastoral` role — prayer requests are either public (via the bot API with a shared key) or inaccessible from the website admin; no role-based restriction to designated pastoral staff; (2) the `editor` role has visitor data access (`content:visitors:read`) including full name and phone number, which exceeds content editing needs; (3) the legacy JSON giving route does not apply PII masking for non-super_admin roles (though access is currently restricted to super_admin only, the code does not enforce masking as a defence-in-depth); (4) no `analytics:read` or `contact:read` permission exists in the permission matrix — `analytics:read` and `giving:read` permissions are used in the code but not listed in any role's grants, meaning only `super_admin` can access them (correct but undocumented).

**Remediation**:
1. Add a `pastoral` role to `admin-permissions.js` with `content:prayer:read` permission. Create a separate admin route for viewing prayer requests that checks this permission.
2. Remove `content:visitors:read` from the `editor` role or replace it with `content:visitors:aggregate` that returns counts only, not full PII.
3. Add PII masking to the legacy `GET /api/admin/giving` route consistent with `giving-admin.routes.ts`.
4. Document all permissions in a human-readable access control matrix visible to the church data controller.

#### access-02 Data Subject Rights (NDPR) — Score: 4/10

**Evidence**:
- `bot/src/routes/privacy.js:44–61` — `POST /bot/api/privacy/visitors/:id/erase` — calls `eraseVisitorData()` which: soft-deletes prayer_requests, event_rsvps, member_profiles; calls `redactVisitorById` which replaces name/email with "Erased Member"/"null", sets `phone_number = CONCAT('erased-', id)`.
- `bot/src/services/visitor.repository.js:375–399` — `redactVisitorById` executes a comprehensive PII redaction on the `visitors` row. Records a `privacy_redacted_at` timestamp.
- `bot/src/services/privacy.repository.js:4–63` — `eraseVisitorData` cascades the soft-delete across prayer_requests, event_rsvps, and member_profiles.
- However, the erasure does **not** cover: `messages` table (sent message text and visitor_id link), `conversation_feedback` table, `opt_outs` table (phone number retained for suppression — which may be legitimate under NDPR), `giving_transactions` (financial records — retention needed for accounting purposes but subject to data minimisation after retention period).
- `bot/src/routes/privacy.js:63–72` — Retention purge endpoint exists but is admin-triggered only.
- No public-facing process for submitting an erasure or access request is documented anywhere on the website.
- No email address or contact for data subject requests is published.
- `src/App.jsx:130–140` — no `/privacy`, `/data-requests`, or `/contact-dpo` route exists.
- `bot/DATA_MODEL_POLICY.md`, `bot/BACKUP_RECOVERY.md` — internal documentation exists, but not linked from any user-facing page.

**Findings**: The technical capability for erasure is materially more advanced than most small church applications — `redactVisitorById` is genuinely thoughtful, preserving the visitor row as a tombstone while replacing all PII fields. The cascade to related tables is correct for prayer_requests, event_rsvps, and member_profiles. The critical gap is that this mechanism exists only in the internal admin API; there is no process by which a data subject could submit a deletion or access request. NDPR Section 3.1(5) requires organisations to inform data subjects of their rights and provide a means to exercise them. Currently: no published contact, no web form, no documented process. Additionally, the erasure does not propagate to `messages` (message history), `conversation_feedback`, or the Paystack-held giving records.

**Remediation**:
1. Publish a data request email address on the privacy policy page (e.g., `privacy@fgcmgbuoba.org`).
2. Create a simple documented process: "Email [address] with subject 'Data Request — [your phone number or name]'. We will respond within 7 working days."
3. Extend `eraseVisitorData` to also soft-delete `messages` and `conversation_feedback` records linked to the visitor.
4. Document that `opt_outs` records are retained for suppression purposes (legitimate interest) even after erasure.
5. Investigate Paystack data deletion procedures for donor records and document what can and cannot be deleted.

### Technical Data Protection

#### sec-01 Data in Transit — Score: 5/10

**Evidence**:
- `bot/src/db/connection.js:11–19` — `new Pool({ connectionString: env.DATABASE_URL, max: 20, ... })` — no explicit `ssl` option in the pool configuration. PostgreSQL SSL would need to be enforced via the connection string (`?sslmode=require`) or pool config `ssl: { rejectUnauthorized: true }`.
- `env/.env.production.example:51` — `DATABASE_URL=postgresql://user:password@prod-db:5432/church_bot` — no `?sslmode=require` suffix in the example.
