# Frontend Best Practices Evaluation — FGC Upper Room Website
**Date**: 2026-05-20
**Evaluator**: Claude Code (automated)
**Framework Version**: frontend-v1

---

## Executive Summary

**Overall Weighted Score**: 6.3 / 10
**Critical Findings (score 1–2)**: 1
**Poor Findings (score 3–4)**: 5

The FGC Upper Room frontend is a well-architected React 18 + Vite 5 SPA with genuine strengths: all 12 routes are fully lazy-loaded with `React.lazy()` and `Suspense`, admin tab panels are also individually lazy-loaded, the heading hierarchy and semantic HTML structure are largely sound, ARIA roles and labels are applied throughout, focus management is implemented in every modal, and a working Nigerian Pidgin (Naija Pidgin) internationalisation system covers the entire public site. The `motion` animation library and `lucide-react` are correctly tree-shaken into separate vendor chunks.

However, three issues are severe for the target audience (mobile users on 3G/4G in Nigeria). The most critical is the image pipeline: 11 of 12 photos in `public/assets/media/pictures/` are uncompressed PNGs ranging from 3.4 MB to 13 MB each, with no WebP conversion, no responsive `srcset`, and no lazy loading on the Team and About page portraits — a single page visit can trigger 20–70 MB of image downloads before the browser has a chance to prioritise. The single JS bundle (193 KB, all code paths merged) is the second major issue: there are no separate runtime chunks, and the vendor manual-chunking in `vite.config.js` is not functioning because the build artefacts show only one JS file (`index-Bk0OWLgi.js`). The third gap is the complete absence of PWA infrastructure: no `manifest.json`, no service worker, and no offline fallback — critical for a congregation on variable connectivity.

## Detailed Findings

### PERFORMANCE — Performance & Loading

#### perf-01 Bundle Size & Code Splitting — Score: 6/10

**Evidence**: `vite.config.js:15–47` — manual chunks defined for react-dom, router, react, lucide, motion; `dist/assets/` — single `index-Bk0OWLgi.js` (193 KB); `src/App.jsx:11–23` — all 12 route pages use `React.lazy()`; `src/pages/Admin/AdminContentPanel.jsx:4–15` — all 12 admin tab panels individually lazy-loaded via `React.lazy()`; `src/pages/Admin/adminPreloaders.js` — idle-time preloading of admin components after authentication.

**Findings**: Route-based code splitting is excellent. Every public page and every admin sub-panel is lazy-loaded with `Suspense` fallbacks. The `adminPreloaders.js` system uses `requestIdleCallback` to speculatively preload admin modules after login — a production-grade pattern. However, the manual `manualChunks` function in `vite.config.js` is not producing separate chunk files in the current build output: the `dist/assets/` directory contains only one `index-*.js` file (193 KB), meaning react-dom (~130 KB source), react-router-dom, lucide-react, and motion/react are all bundled together. This negates the benefit of separate caching for stable vendor dependencies. The `modulePreload: { polyfill: false }` setting at `vite.config.js:12` is a valid optimisation for modern browsers but removes the polyfill for older Android WebView users. No barrel-file tree-shaking issues were found: lucide is imported icon-by-icon, not `import * from 'lucide-react'`.

**Remediation**: (1) Verify the `manualChunks` function is running — add a `console.log` in development or run `npx vite-bundle-visualizer` to diagnose why chunks are not splitting. Vite 8 may require `output.chunkFileNames` to be set. (2) Confirm the build is being run with `vite build` (not `vite build --mode development`). (3) Consider adding `vendor-motion` and `vendor-lucide` as dynamic imports within their consuming components if they are only needed on specific pages. (4) The 193 KB bundle is under the 200 KB gzip threshold when compressed (~58 KB gzip), so initial load is acceptable — the main benefit of chunk splitting here is cache longevity.

#### perf-02 Image Optimization — Score: 2/10

**Evidence**: `public/assets/media/pictures/IMG_1769.png` — 13 MB; `public/assets/media/pictures/IMG_1784.png` — 4.9 MB; `src/pages/About/About.jsx:8` — `const youthPhoto = toAssetUrl('assets/media/pictures/IMG_1769.png')`; `src/pages/About/About.jsx:71` — `<img src={youthPhoto} alt="Upperroom Youth Church" />` (no `loading`, no `width`, no `height`); `src/pages/Team/Team.jsx:33–68` — 9 PNG files referenced, none with `loading="lazy"`, `width`, or `height`; `src/pages/Home/PastorWelcome.jsx:3` — `Senior Pastor_Home.jpeg` (71 KB, JPEG — the one correctly formatted image); `src/pages/Home/HeroSection.jsx:10–15` — four icon PNGs used as hero decoration; `index.html` — no `<link rel="preload">` for hero images; `dist/assets/images/` — empty (images served from `public/`, not processed by Vite); no WebP files found anywhere in `public/`.

**Findings**: This is the most severe performance issue on the site. 11 of 12 photos are uncompressed PNGs saved at full camera resolution. `IMG_1769.png` at 13 MB is loaded on the About page with no `loading="lazy"`, no `width`/`height` attributes (causes Cumulative Layout Shift), no `srcset`, and no WebP alternative. The Team page references 9 of these files simultaneously. The four Foursquare icon PNGs in the hero (cross: 14 KB, dove: 91 KB, cup: 51 KB, crown: 67 KB) are rendered as ~80px decorative elements but loaded at full resolution. `favicon.png` is 91 KB — unnecessarily large for a favicon. The `BlogCard.tsx:42` and Media page do use `loading="lazy"` for user-uploaded content, but the static site portraits do not. There are zero WebP images in the project. No hero image preload link exists in `index.html`.

**Remediation**: (1) Convert all PNGs in `public/assets/media/pictures/` to WebP using `cwebp` or Squoosh at 80% quality — expected reduction: 13 MB → ~350 KB. (2) Add `width` and `height` attributes (or CSS `aspect-ratio`) to all `<img>` elements to prevent CLS. (3) Add `loading="lazy"` to all below-fold images (`About.jsx:71`, all `Team.jsx` portrait `<img>` elements). (4) Add `<link rel="preload" as="image">` for the hero wordmark (`upper_white.png`) in `index.html`. (5) Convert `favicon.png` (91 KB) to a 32×32 ICO or 96×96 WebP. (6) Consider Vite image optimisation plugins (`vite-imagetools`, `vite-plugin-image-optimizer`) to automate format conversion at build time.

#### perf-03 Font Loading — Score: 6/10

**Evidence**: `index.html:11–13` — `<link rel="preconnect" href="https://fonts.googleapis.com">` + `<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>` + Google Fonts URL with `&display=swap`; `src/styles/variables.css:82–83` — `--font-body: 'Manrope', -apple-system, BlinkMacSystemFont, sans-serif` and `--font-heading: 'Spectral', Georgia, serif`; `index.html:14` — Font Awesome 6.5.1 loaded from cdnjs.cloudflare.com as a render-blocking `<link rel="stylesheet">` (no `async`, no `defer`).

**Findings**: Google Fonts are loaded with `display=swap` (correct — prevents FOIT), `preconnect` hints for both googleapis and gstatic are present (correct). Fallback fonts are specified in the CSS variable stack: `-apple-system, BlinkMacSystemFont, sans-serif` for body and `Georgia, serif` for heading. This means text renders immediately with system fonts before Manrope/Spectral load. However, Font Awesome 6.5.1 (all.min.css from CDN, ~900+ icons, ~60–80 KB gzip) is loaded as a render-blocking stylesheet. The site uses Font Awesome icons extensively via `<i className="fa-solid fa-...">` across every page. This is a genuine render-blocking resource that delays First Contentful Paint. Fonts are not self-hosted — Google Fonts requires a separate DNS/TLS handshake even with preconnect, adding 100–300ms on first visit for Nigerian CDN routing. No `<link rel="preload" as="font">` exists for the most critical font files.

**Remediation**: (1) Convert Font Awesome to `font-display: swap` by self-hosting it or using a subset build — only a fraction of the 900+ icons are actually used. Alternatively, replace Font Awesome icons with `lucide-react` (already a dependency) which is already tree-shaken. (2) Consider self-hosting Manrope and Spectral (download WOFF2 subset for Latin + Latin-Extended) to eliminate the Google Fonts network round-trip for repeat visitors. (3) Add `<link rel="preload" as="font" type="font/woff2" crossorigin>` for Manrope regular and Spectral regular WOFF2 files.

#### perf-04 Core Web Vitals Readiness — Score: 5/10

**Evidence**: `index.html:14` — Font Awesome stylesheet render-blocking; `src/pages/About/About.jsx:71` — 13 MB PNG above fold, no width/height; `src/styles/globals.css:278–285` — `prefers-reduced-motion` media query applied globally; `index.html:19` — Paystack JS loaded with `defer` (correct); `src/styles/globals.css:145–148` — `:focus-visible` outline defined globally with `color-mix`; `src/pages/Home/Home.css:278` — `aspect-ratio: 16/9` and `:313` — `aspect-ratio: 3/4` (two sections use explicit aspect ratios — good for CLS); `src/App.jsx:46` — `requestAnimationFrame` used for scrollbar theme updates; `src/styles/globals.css:81–82` — `overflow-x: hidden` on both `html` and `body`.

**Findings**: **LCP**: The Largest Contentful Paint element on the home page is likely the hero wordmark image (`upper_white.png`, 25 KB), which is not preloaded in `<head>`. On About/Team pages, LCP is the uncompressed PNG (13 MB / 3–6 MB) which will be catastrophically slow on mobile. LCP target of 2.5s is impossible for About/Team on 3G. **CLS**: Some sections use `aspect-ratio` (Home hero icons, pastor welcome grid at CSS level), but the major portrait images on About/Team have no dimensions — they will cause layout shift as the browser discovers their natural dimensions after download. `overflow-x: hidden` on `body` can mask horizontal scroll issues. **INP**: Minimal JS on user interactions — the `MutationObserver` in `App.jsx:77–91` for i18n literal translations runs on every DOM mutation across the entire document with a 100ms debounce. On lower-end Android phones this could add perceptible input delay during page transitions and DOM updates. **Render-blocking**: Font Awesome CSS in `<head>` without `media="print"` trick or async loading.

**Remediation**: (1) Fix the image sizes (perf-02 addresses this). (2) Add `fetchpriority="high"` to the hero wordmark `<img>`. (3) Consider scoping the `MutationObserver` in `App.jsx` to avoid watching `attributes: true` on the entire document — restrict `attributeFilter` further or observe specific subtrees. (4) Profile with Lighthouse on a throttled mobile connection to identify the actual LCP element per page.

#### perf-05 PWA Readiness — Score: 1/10

**Evidence**: `public/` directory contains only `assets/`, `favicon.png`, and `index.html` — no `manifest.json` or `manifest.webmanifest`; no service worker file found anywhere in `public/` or `src/`; `vite.config.js:9` — only `@vitejs/plugin-react` plugin, no `vite-plugin-pwa`; `package.json:58–67` — devDependencies contain no `vite-plugin-pwa`, `workbox-*`, or service worker packages; `index.html` — no `<link rel="manifest">`.

**Findings**: PWA infrastructure is completely absent. There is no web app manifest, no service worker, no offline fallback, and no install prompt capability. The site is not installable on Android or iOS home screens. For a church congregation in Mgbuoba on variable 3G/4G, the inability to cache service times, the contact page, and the events page offline is a meaningful usability gap. The framework notes this as a strategic feature and the `index.html` contains `<meta name="theme-color" content="#8a161e">` (present — good start), but that alone does not satisfy PWA installability criteria. `<link rel="apple-touch-icon">` points to the 91 KB `favicon.png` rather than a purpose-built icon.

**Remediation**: (1) Add `vite-plugin-pwa` (or `@vite-pwa/vite-plugin`) to `devDependencies`. (2) Create `public/manifest.webmanifest` with `name: "FGC Upper Room"`, `short_name: "UpperRoom"`, `start_url: "/"`, `display: "standalone"`, `theme_color: "#8a161e"`, and icon entries at 192×192 and 512×512 (create optimised PNG icons from `logo-color.png`). (3) Configure a Workbox `NetworkFirst` strategy for API calls and `CacheFirst` for static assets. (4) Create an offline fallback page showing service times (static HTML — already in footer JSX). (5) Add `<link rel="manifest" href="/manifest.webmanifest">` to `index.html`.

#### a11y-02 ARIA & Screen Reader Support — Score: 7/10

**Evidence**: `src/pages/Home/HeroSection.jsx:67–70` — icon images have meaningful alt text ("Jesus the Savior symbol", "Jesus the Baptizer symbol", etc.); `src/pages/Home/PastorWelcome.jsx:11` — `alt="Pastor Photo"` (generic — could be more descriptive); `src/components/common/LoadingScreen/LoadingScreen.jsx:28` — decorative loading icons have `alt=""` (correct); `src/pages/Contact/Contact.jsx:190–198` — all form inputs have associated `<label htmlFor>` labels; `src/App.jsx:124` — `<a className="skip-link" href="#main-content">Skip to main content</a>`; `src/components/common/Feedback/FeedbackProvider.jsx:78` — `aria-live="polite" aria-atomic="true"` on toast stack; `src/components/common/LoadingScreen/LoadingScreen.jsx:13` — `role="status" aria-live="polite"`; `src/components/features/GivingModal/PaystackFlow.jsx:60` — `role="alert"` on error; `src/pages/Events/Events.jsx:53` — `<img src={featuredEvent.image} alt={featuredEvent.title} />` (dynamic alt from event title); `src/components/layout/Footer/Footer.jsx:155–161` — social links have `title` but no `aria-label` (relying on `title` for screen readers is insufficient).

**Findings**: ARIA support is well above average. The skip-to-content link exists and is visually hidden until focused (`globals.css:150–168`). Form labels are correctly associated via `htmlFor`. Live regions are used for toasts, loading screens, and form status messages. Error messages in all three giving flows use `role="alert"`. Modal dialogs consistently use `role="dialog" aria-modal="true"` with `aria-labelledby` references. However, there are gaps: (1) The footer social links (`Footer.jsx:148–161`) use only `title` for screen reader identification — `title` attributes are not reliably announced by all screen readers; they should have `aria-label`. (2) The pastor photo at `PastorWelcome.jsx:11` has `alt="Pastor Photo"` — this is unhelpfully generic; it should identify the person ("Rev. Dr. Martins Okoro, Senior Pastor"). (3) The contact form status message (`Contact.jsx:184–188`) renders as a `<p>` element with a CSS class, but has no `role="alert"` or `aria-live` — error messages on form submission will not be automatically announced to screen readers. (4) The `aria-label` missing from the Events featured image (`Events.jsx:53`) when the image is purely decorative to the event description (both the image and the title text convey the same content — the image could be `aria-hidden="true"`).

**Remediation**: (1) Add `aria-label={social.label}` to all social link anchors in `Footer.jsx`. (2) Update `alt="Pastor Photo"` to `alt="Rev. Dr. Martins Okoro, Senior Pastor, FGC Mgbuoba Zonal HQ"`. (3) Add `role="alert"` or wrap `Contact.jsx:184–188` status paragraph in a `aria-live="polite"` region so screen readers announce submission results. (4) Consider `aria-hidden="true"` on the featured event image in `Events.jsx:53` to avoid duplicate content announcements with the `<h2>{featuredEvent.title}</h2>` that follows.

#### a11y-03 Keyboard Navigation — Score: 7/10

**Evidence**: `src/styles/globals.css:145–148` — `:focus-visible { outline: 3px solid color-mix(...); outline-offset: 3px; }` (global focus style, not removed); `src/components/layout/Header/Header.jsx:61–68` — Escape key handler closes mobile menu and returns focus to toggle; `src/pages/Home/HeroSection.jsx:37–54` — manual focus trap on address modal (Escape, Tab, Shift+Tab all handled); `src/components/layout/Footer/Footer.jsx:104–108` — Escape closes language dropdown and returns focus to trigger; `src/pages/Events/Events.jsx:33–34` — `closeEventModal` returns focus to trigger element via `activeModalTriggerRef`; `src/pages/Admin/components/AdminSidebar.jsx:30–31` — hover and focus on sidebar buttons triggers component preloading (good UX); `src/pages/Media/Media.css:161` — `outline: none` on filter buttons without focus-visible replacement; `src/pages/Events/Events.css:255` — `outline: none` on carousel nav button; `src/pages/Contact/Contact.css:205–207` — `outline: none` on select trigger on `:focus` (not `:focus-visible`).

**Findings**: Keyboard navigation is implemented with care. Focus return after modal close is correctly handled in all reviewed components. Escape dismissal works in all modals. The `:focus-visible` CSS pattern in `globals.css` is the right approach. However, there are 14 instances of `outline: none` in page-level CSS files that apply on plain `:focus` rather than the `:-webkit-focus-visible` / `:focus-visible` pseudo-class. For the Media page filter buttons and Events carousel buttons, keyboard users lose visible focus indicators. The Contact form's custom dropdown select (`DropdownSelect` component) removes the default outline on `:focus` and replaces it with a `border-color` change — this is a usable custom focus indicator, but it applies to the entire `:focus` state (mouse + keyboard) rather than only keyboard focus via `:focus-visible`. The header mobile toggle correctly exposes `aria-expanded` and `aria-controls` (lines 121–122), and the nav links use `aria-current="page"` (line 99).

**Remediation**: (1) Replace all `outline: none` on `:focus` selectors in page CSS with either `outline: none` on `:focus:not(:focus-visible)` or simply rely on the global `:focus-visible` rule. Affected files: `Blog.css:86`, `Contact.css:207`, `Events.css:255,1248,1297`, `Home.css:819`, `Media.css:161,311,343,458`. (2) Ensure the custom `DropdownSelect` component shows a visible focus ring when navigated by keyboard — test with Tab key on the contact form subject field.

#### a11y-04 Color & Contrast — Score: 6/10

**Evidence**: `src/styles/variables.css:8–11` — `--cross-red: #8a161e`, `--cup-blue: #2d3a7a`, `--crown-purple: #5a4494`; `src/styles/globals.css:83–88` — `color: var(--dark)` (`#1a1a1a`) on `background: var(--white)` (`#ffffff`); `src/components/layout/Header/Header.css:73` — `.header__link { color: var(--gray-700) }` where `--gray-700: #5c5c5c` on white background; `src/styles/variables.css:40` — `--gray-700: #5c5c5c`.

**Findings**: Several colour combinations require contrast analysis against WCAG AA (4.5:1 for normal text): **`#1a1a1a` on `#ffffff`**: 18.1:1 — passes. **`#5c5c5c` (gray-700, nav links on white)**: 7.0:1 — passes AA and AAA. **`#8a161e` (cross-red) on white**: ~7.5:1 — passes. **`#2d3a7a` (cup-blue) on white**: ~10.5:1 — passes. **`#5a4494` (crown-purple) on white**: ~6.8:1 — passes. The gradient backgrounds use white text: white on `linear-gradient(135deg, #8a161e, #6b1118)` (darkest point ~7.0:1) passes. The `page-banner p` uses `rgba(255,255,255,0.8)` on red gradient — at 80% opacity the effective contrast is approximately 4.2:1 which is borderline for normal-sized text (WCAG AA requires 4.5:1). The `.hero__tagline` text uses white on the dark hero overlay — not easily calculable without knowing the exact overlay opacity and background image, but the dark overlay at 70% opacity (`rgba(0,0,0,0.7)` at bottom) should ensure sufficient contrast. Information is conveyed through both color and text throughout. Links in nav use active color + background, not just color alone.

**Remediation**: (1) Increase `page-banner p` colour from `rgba(255,255,255,0.8)` to `rgba(255,255,255,0.95)` or pure white to safely clear the 4.5:1 ratio on gradient backgrounds. (2) Verify the hero tagline contrast using the exact overlay opacity at the text position — Lighthouse contrast checker will catch this. (3) Run an automated contrast check with axe-core or Lighthouse on all page banners.

## Mobile-Specific Issues

1. **Image payload is catastrophic on mobile**: Visiting the Team or About page on a 3G connection triggers 30–70 MB of uncompressed PNG downloads. This is likely to result in browser OOM errors or multi-minute load times on budget Android devices common in Nigeria. **Priority: P0**.

2. **No offline access**: Church members checking service times while offline (e.g., in areas with no signal) see a blank screen. Service times are in static JSX and would be available with even a basic service worker cache. **Priority: P1**.

3. **Font Awesome render-blocking**: The 60–80 KB Font Awesome stylesheet in `<head>` without async/defer adds 300–800ms to First Contentful Paint on 3G. On a device already under memory pressure from the page, this compounds with image loading. **Priority: P1**.

4. **No PWA install prompt**: Nigerian users on Android Chrome cannot add the app to their home screen for quick access to service times and giving. This is a missed engagement opportunity. **Priority: P1**.

5. **Blog and Events silent API failures**: When the API is unreachable, the Blog page shows an empty list with no loading indicator or error message. A member looking for devotionals on Sunday morning will see a blank page and assume there is no content. **Priority: P2**.

6. **MutationObserver i18n overhead**: The DOM-walking `MutationObserver` runs on every DOM mutation across the entire document for the PCM translation pass. On a Qualcomm Snapdragon 430 (typical budget Android), this can add 50–150ms of main-thread blocking per navigation — contributing to high INP. **Priority: P2**.

7. **`outline: none` on form inputs on `:focus`**: Mobile users who pair a physical keyboard with their phone lose focus indicators on the custom select dropdown in Contact form and Media filter buttons. **Priority: P3**.
