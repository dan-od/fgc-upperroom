## Executive Summary

**Overall Weighted Score**: 6.4 / 10 ▲ +1.2 from 2026-05-19
**Critical Findings**: 0 (was 4)
**Poor Findings**: 4 (was 7)

Six previously Critical or Poor findings have been remediated since the last evaluation. The four previously-Critical issues are now closed: all `data/*.json` files are in `.gitignore` (secrets-04), the Meta webhook POST handler now verifies `X-Hub-Signature-256` with `crypto.timingSafeEqual` (wa-01), the admin login endpoint now applies `createRateLimit` middleware (auth-04), and the hardcoded `"Admin123!"` fallback and `VITE_ADMIN_PASSWORD` fallback in `admin-auth.js` are removed from source code (secrets-01). Additionally, `helmet()` is now applied to all three Express apps, CORS on the bot and attendance services is now restricted to an explicit origin allowlist, and LLM prompts now use first name only (wa-03/input-04 improvement).

Remaining gaps centre on: admin `sessionStorage` token storage (XSS-accessible), TOTP not enforced for super_admin, no rate limiting on the contact form or newsletter subscribe endpoints, and SSL for PostgreSQL connections is `rejectUnauthorized: false` (accepts self-signed certs) rather than verified certs.

## Detailed Findings

### AUTH — Authentication & Identity

#### auth-01 Password Storage — Score: 5/10 (unchanged)
**Evidence**: `src/api/auth.utils.ts:6-8` — `crypto.pbkdf2Sync(password, salt, 120000, 64, "sha512")`.
**Findings**: Algorithm remains PBKDF2-SHA512 at 120,000 iterations. The hardcoded `"Admin123!"` fallback in `src/api/app.ts` has been removed — no match found on grep. The `VITE_ADMIN_PASSWORD` fallback in `bot/src/lib/admin-auth.js` has also been removed. References to `VITE_ADMIN_PASSWORD` remain in documentation files (`bot/DEPLOYMENT.md:106`, `bot/README.md:111`, `bot/ENV_SECRETS_SETUP.md:85`) but not in executed source code. PBKDF2-SHA512 at 120k iterations is cryptographically acceptable but Argon2id remains the recommended standard for new implementations.
**Status**: `secrets-01` critical removed; algorithm weakness remains.

---

#### auth-02 Session Management — Score: 5/10 (unchanged)
**Evidence**: `src/utils/adminApi.js:8,17` — `sessionStorage.setItem(ADMIN_SESSION_TOKEN_KEY, token)`.
**Findings**: Tokens remain in `sessionStorage` (XSS-accessible). Session generation with `crypto.randomBytes(48)` and server-side invalidation on logout are both still correct. No change to HttpOnly cookie approach.
**Remediation**: Switch admin token to `HttpOnly; Secure; SameSite=Strict` cookie.

---

#### auth-03 MFA/TOTP — Score: 4/10 (unchanged)
**Evidence**: `src/api/admin.routes.ts:76-84` — TOTP checked only when `user.twoFactorEnabled && user.twoFactorSecret`. No enforcement for super_admin.
**Findings**: No change. TOTP infrastructure works but is optional for all roles including super_admin.

---

#### auth-04 Brute Force Protection — Score: 6/10 ▲ (was 2/10)
**Evidence**: `src/api/admin.auth.ts:14` — `createRateLimit` middleware applied to `/api/admin/auth/login` and `/api/admin/auth/password-reset/confirm`.
**Findings**: Rate limiting is now applied on the login and password-reset paths. The `createRateLimit` helper is a centralised factory rather than the hand-rolled per-route pattern. Score increases from 2 → 6. Remaining gap: account lockout after N failures is not implemented (only IP-rate limiting), and the rate limit does not use Redis (so it resets on process restart).

2. **[POOR]** `auth-03` — TOTP not enforced for `super_admin`. Block login if `twoFactorEnabled === false` for super_admin role. — `src/api/admin.routes.ts:76`

5. **[MODERATE]** `crypto-03` — PostgreSQL SSL uses `rejectUnauthorized: false` (accepts any cert). Upgrade to `rejectUnauthorized: true` with a verified CA cert in production. — `bot/src/db/connection.js:18`

6. **[MODERATE]** `secrets-04` — Git history still contains previously-committed `data/*.json` files with password hashes, session tokens, and donor PII. Run `git filter-repo` to purge history and rotate all affected credentials. — (git history)

7. **[MODERATE]** `wa-03` — LLM output used directly without post-response length validation or content filtering. A misbehaving LLM could send excessive text or unexpected content to congregation members. — `bot/src/services/message-generator.service.js:397-416`

8. **[MODERATE]** `wa-01` — `META_APP_SECRET` absence skips signature verification rather than rejecting the request. Add a startup warning (or startup failure in production) if `META_APP_SECRET` is not set. — `bot/src/app.js:111`
