## Pipeline Security Assessment

The CI pipeline (`ci.yml`) triggers on pull requests to `main` and runs env parity check, unit/integration/E2E tests, security smoke checks, performance checks, load checks, and a build. The deploy pipeline (`deploy.yml`) triggers on push to `main` and `workflow_dispatch`, re-runs unit tests and the QA gate before deploying. Deployment uses Tailscale OAuth (via a third-party action at `tailscale/github-action@v2`) to establish a VPN tunnel before SSH/rsync to the production host. Secrets for Tailscale, SSH key, deploy host, user, path, and nginx container name are all sourced from GitHub Secrets — no hardcoded production credentials in the workflow YAML.

Key gaps: Actions are pinned to `@v2`/`@v4` tags, not SHA hashes (supply chain risk). No `permissions:` stanza means all jobs inherit the default `GITHUB_TOKEN` scope, which is `contents: write` for push events. `npm audit` is absent from both pipelines. `BOT_ADMIN_API_KEY: ci-admin-key` and `VITE_ADMIN_PASSWORD: ci-admin-key` are hardcoded in the CI `env:` block (acceptable for CI but documented as a known pattern). `StrictHostKeyChecking=no` is used on all three SSH calls in the deploy job, defeating TOFU host-key verification.

## Detailed Findings

### CI/CD Pipeline Security

#### ci-01 GitHub Actions Security — Score: 5/10

**Evidence**:
- `.github/workflows/ci.yml:45` — `actions/checkout@v4` (tag, not SHA)
- `.github/workflows/ci.yml:49` — `actions/setup-node@v4` (tag, not SHA)
- `.github/workflows/ci.yml:84` — `actions/upload-artifact@v4` (tag, not SHA)
- `.github/workflows/deploy.yml:74` — `tailscale/github-action@v2` (tag, not SHA)
- Neither workflow file contains a `permissions:` stanza
- `ci.yml` triggers on `pull_request` — PR workflows from forks cannot access secrets by default (safe)
- No evidence of branch protection configuration in the repository source (documented `dykdee` collaborator in framework context)

**Findings**: All five GitHub Actions used across both workflows are pinned to version tags (`@v2`, `@v4`) rather than immutable commit SHA hashes. Tag pinning is insufficient for supply-chain security: a malicious actor who gains control of the `actions/checkout` or `tailscale/github-action` repositories could push a new commit to the `v4` or `v2` tag and have it silently executed in the next workflow run. The `tailscale/github-action@v2` is a third-party action with access to `TS_OAUTH_SECRET` — a particularly high-risk unpinned action because compromise would allow hijacking the VPN tunnel to reach the production host. Neither workflow defines a `permissions:` stanza. For push events (which trigger `deploy.yml`), the default `GITHUB_TOKEN` scope is `contents: write`, `issues: write`, `pull-requests: write`, and others — far more than the deploy workflow needs (which requires only `contents: read` at most). The CI workflow triggers on `pull_request` for `main` branch PRs; by default, fork PRs cannot access secrets, which is the safe behavior and correctly in place.

**Remediation**:
1. Pin all actions to commit SHAs. Use `actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683` (v4 HEAD SHA at time of writing; verify current) and similarly for other actions.
2. Add `permissions: contents: read` (or `permissions: {}`) to both workflow files as a job-level default to enforce least privilege.
3. For the `tailscale/github-action`, verify its SHA at the current `v2` tag before pinning: `gh api repos/tailscale/github-action/git/ref/tags/v2`.

#### ci-02 Secret Management in CI — Score: 7/10

**Evidence**:
- `deploy.yml:76` — `oauth-client-id: ${{ secrets.TS_OAUTH_CLIENT_ID }}`
- `deploy.yml:77` — `oauth-secret: ${{ secrets.TS_OAUTH_SECRET }}`
- `deploy.yml:82` — `echo "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/deploy_key`
- `deploy.yml:84` — `ssh-keyscan -H ${{ secrets.DEPLOY_HOST }} >> ~/.ssh/known_hosts`
- `deploy.yml:90` — `${{ secrets.DEPLOY_USER }}@${{ secrets.DEPLOY_HOST }}:${{ secrets.DEPLOY_PATH }}/`
- `deploy.yml:100` — `docker restart ${{ secrets.NGINX_CONTAINER }}`
- `deploy.yml:103` — `if: always()` / `run: rm -f ~/.ssh/deploy_key` (SSH key cleanup)
- `ci.yml:38` — `BOT_ADMIN_API_KEY: ci-admin-key` (hardcoded CI value)
- `ci.yml:39` — `VITE_ADMIN_PASSWORD: ci-admin-key` (hardcoded CI value)

**Findings**: Production secrets (Tailscale OAuth, SSH private key, deploy host/user/path, nginx container name) are correctly sourced from GitHub Secrets. The SSH private key is written to disk, used, and then deleted in an `if: always()` cleanup step at `deploy.yml:101–103` — this is good practice. However, three SSH calls at lines 88, 93, and 98 use `-o StrictHostKeyChecking=no`, which disables host key verification. This means a MITM attack that redirects the Tailscale tunnel could intercept the deployment without triggering a warning. The `ssh-keyscan` at line 84 does populate `known_hosts`, but the subsequent `-o StrictHostKeyChecking=no` overrides it, making the `known_hosts` step useless. The hardcoded CI values (`ci-admin-key`) are acceptable for test fixtures but are used as actual `BOT_ADMIN_API_KEY` and `VITE_ADMIN_PASSWORD` in the CI environment — the security smoke test at `scripts/security-smoke.mjs` runs against the live bot with `BOT_ADMIN_API_KEY=test-admin` (from `package.json:36`), so the CI key is not a production leak. No secrets are echoed in any script. No evidence of periodic rotation documentation for the Tailscale OAuth token or the SSH deploy key.

**Remediation**:
1. Remove `-o StrictHostKeyChecking=no` from all SSH/rsync calls. Instead, rely on the `ssh-keyscan` output that is already being written to `known_hosts`. This restores host key verification.
2. Document a rotation schedule for `TS_OAUTH_SECRET` and `SSH_PRIVATE_KEY` in `OPERATIONS.md`.
3. The SSH deploy key should be scoped to a restricted deploy user with `command=` restriction in `authorized_keys` on the server (allows only the rsync + docker restart commands). This **requires server-side implementation** — see Manual Verification section.

#### ci-03 Build & Deploy Process — Score: 6/10

**Evidence**:
- `deploy.yml:9` — deploys only on `push: branches: [main]` and `workflow_dispatch`
- `deploy.yml:8–57` — `test` job must complete (`needs: test`) before `build-and-deploy`
- `deploy.yml:54` — `run: npm ci` (deterministic install)
- `ci.yml:54` — `run: npm ci` (deterministic install)
- `deploy.yml:67–68` — `npm ci` then `npm run build` before deploy
- `deploy.yml:88–90` — rsync with `--delete` (replaces files atomically at directory level)
- `bot/DEPLOYMENT.md:460–475` — rollback procedure documented (PM2 / Docker / systemd variants)

**Findings**: Deployment correctly gates on branch (`main` only) and requires the test job to pass first. `npm ci` is used throughout — deterministic, lockfile-enforced installs. Build artifacts are generated fresh before each deploy. A rollback procedure is documented in `bot/DEPLOYMENT.md:458–484`, covering PM2, Docker, and systemd approaches with git checkout to a previous tag. The deploy uses rsync `--delete` which atomically replaces the dist directory on the remote host, then restarts the nginx/Docker container. However: (1) The deploy job checks out fresh code and runs `npm ci` + `npm run build` independently of the `test` job — meaning the build runs against the same commit SHA but there is no explicit artifact handoff between jobs (the CI job uploads an artifact in `ci.yml` but the deploy pipeline does not download and use it; it rebuilds). (2) No checksum or signature verification of the build output before deployment. (3) `workflow_dispatch` allows manual triggering bypassing the branch push condition — any collaborator who can trigger workflows could deploy from an arbitrary commit if combined with GitHub's workflow dispatch.

**Remediation**:
1. Share the build artifact between the `test` and `build-and-deploy` jobs to avoid a redundant build and ensure the tested artifact is the deployed artifact (use `actions/upload-artifact` + `actions/download-artifact`).
2. Add a deploy lock or concurrency group (`concurrency: group: deploy-production`) to prevent concurrent deployments.
3. Consider requiring a manual approval step for `workflow_dispatch` deploys via GitHub Environments.

#### ci-04 Automated Security Checks in Pipeline — Score: 3/10

**Evidence**:
- `ci.yml:71–72` — `Run security smoke checks: npm run qa:security` (runs `scripts/security-smoke.mjs`)
- `scripts/security-smoke.mjs:37–48` — checks HTTP security headers and admin key rejection on the bot
- `ci.yml` (no `npm audit` step), `deploy.yml` (no `npm audit` step)
- `package.json` — no `eslint`, `eslint-plugin-security`, `semgrep`, `snyk`, or `codeql` in devDependencies
- No SAST workflow file under `.github/workflows/`

**Findings**: The security smoke check that runs in CI (`qa:security` / `scripts/security-smoke.mjs`) is a functional runtime check: it spins up the bot Express app, verifies security headers are present, and verifies the admin key is enforced. This is a useful black-box test but it covers only the bot service header configuration and auth rejection — it does not check the main website API or the attendance service, does not test for SQL injection, and does not detect dependency vulnerabilities. Critically, `npm audit` does **not** run in either the CI or deploy pipeline. The prior security evaluation found 3 high-severity vulnerabilities in `path-to-regexp` and `vite`. These would never be caught automatically by the current pipeline. There is no ESLint, no `eslint-plugin-security`, no SAST tool (Semgrep, CodeQL, Snyk, or similar), and no dependency scanning. This is the most significant CI gap in the entire DevOps posture.

**Remediation**:
1. Add `npm audit --audit-level=high` as a CI step (in both `ci.yml` and `deploy.yml`). This is a one-line addition that catches known critical/high vulnerabilities before deploy.
2. Add ESLint with `eslint-plugin-security` — even a minimal config catches patterns like `new Function()`, `eval()`, and regex-based injection risks.
3. Consider enabling GitHub's free CodeQL scanning via a workflow (`codeql-analysis.yml`) — it integrates with the existing PR workflow and requires no API keys.
4. Expand the security smoke test to cover the main website API's headers and the attendance service.

**Evidence**:
- `scripts/check-env-parity.mjs:6–11` — checks 4 files: `.env.example`, `env/.env.development.example`, `env/.env.staging.example`, `env/.env.production.example`
- `scripts/check-env-parity.mjs:13–47` — `REQUIRED_KEYS` list of 28 critical variables
- `scripts/check-env-parity.mjs:68–111` — set-diff logic comparing baseline against each env file, fails with `process.exitCode = 1` on drift
- `scripts/check-env-parity.mjs:114–120` — additional check that all 28 required keys appear in every file

- `deploy.yml:53–54` — same check runs before the QA gate in the deploy test job
- `package.json:19` — `"env:parity": "node scripts/check-env-parity.mjs"` script defined

**Findings**: The environment parity check is well-implemented and runs at the right point in both workflows (before tests, before deploy). It uses a set-diff approach: the baseline is `.env.example` and all other env files must have exactly the same keys (no missing, no extra). It also validates 28 named required keys are present in every file. The script exits with code 1 on failure, blocking the CI/deploy pipeline. Coverage is good — all three environment-specific files are checked against the baseline. One limitation: the check validates key presence but not value format (e.g., it would not catch `DATABASE_URL` being left as the literal placeholder `postgresql://user:password@prod-db:5432/church_bot`). The required keys list covers all critical runtime variables including `META_APP_SECRET`, `BOT_ADMIN_API_KEY`, and `MONITORING_*` thresholds.

2. Consider adding VITE-prefixed keys that should NOT have non-empty values in the production example (e.g., validate `VITE_ENABLE_ADMIN_FALLBACK_LOGIN=false` in the production template).

**Evidence**:
- `bot/DEPLOYMENT.md:314–334` — nginx example block showing proxy headers (`X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`, `Host`, `Upgrade`, `Connection`)
- No nginx config files in repository (no `nginx.conf`, no `sites-available/` directory)

**Findings**: A partial nginx example exists in documentation with correct proxy header forwarding (`X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`) — these are essential for Express to see real client IPs and for HTTPS detection. However, the example omits all security hardening directives. `server_tokens off` is absent (nginx version leakage). No security headers are added at the nginx level (relying on Express apps to set them, but the main website API has limited headers per the security evaluation). No rate limiting directives at the nginx level. No SSL hardening (`ssl_protocols TLSv1.2 TLSv1.3`, `ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:...`). The actual production nginx configuration cannot be evaluated — it **requires manual server verification**.

**[REQUIRES MANUAL VERIFICATION]** — See manual verification section.

**Remediation**:
1. Add `server_tokens off;` to the `http {}` block in nginx.conf.
2. Add security headers at the nginx level: `add_header X-Frame-Options "DENY"; add_header X-Content-Type-Options "nosniff"; add_header Referrer-Policy "no-referrer"; add_header Strict-Transport-Security "max-age=31536000; includeSubDomains";`

4. Add SSL hardening: `ssl_protocols TLSv1.2 TLSv1.3; ssl_prefer_server_ciphers off;` with a modern cipher suite.
5. Commit the nginx config template to the repository under `config/nginx/` for documentation and reproducibility.

#### infra-04 Database & Redis Security — Score: 5/10

**Evidence**:
- `bot/docker-compose.yml:7–10` — `POSTGRES_PASSWORD: ${DB_PASSWORD}` (env var expansion, not hardcoded)
- `bot/docker-compose.yml:9–10` — `POSTGRES_DB: church_bot`, `POSTGRES_USER: botuser`
- `bot/docker-compose.yml:12` — `ports: - "${DB_PORT:-5433}:5432"` (custom port, configurable)
- `bot/docker-compose.yml:22–24` — Redis: no `--requirepass` in command, `ports: - "6379:6379"`
- `bot/docker-compose.yml:44` — `DATABASE_URL: postgresql://botuser:${DB_PASSWORD}@postgres:5432/church_bot`
- `bot/BACKUP_RECOVERY.md:19` — "Encryption: at rest and in transit" documented as policy
- `bot/DEPLOYMENT.md:190–192` — "use read-only database user for reporting queries" documented

**Findings**: PostgreSQL password is correctly sourced from `${DB_PASSWORD}` environment variable — not hardcoded in the compose file. The database user is `botuser` (not a superuser). The postgres port is configurable (`${DB_PORT:-5433}`) and mapped from 5432 internally to 5433 externally by default, reducing opportunistic scanning exposure. Redis is more concerning: the `command:` directive at `docker-compose.yml:21` uses `redis-server` without `--requirepass`, meaning Redis requires no password. Additionally, Redis is bound to `0.0.0.0:6379` (all interfaces), not `127.0.0.1:6379`. In a Docker network context, the `:6379:6379` port mapping exposes Redis on all host interfaces. Any process that can reach the host network (or the host's public IP if the server has one) can access Redis without authentication. BullMQ queue data and job state are stored in this unauthenticated Redis. The `pg_hba.conf` configuration for PostgreSQL cannot be verified from Docker Compose alone — it depends on the Docker postgres image defaults which use `md5` auth for all connections, which is acceptable but not verifiable without server access. Off-site backup encryption is documented as policy but not implemented in the backup script.

**Remediation**:
1. Add Redis password authentication: change the redis `command:` to `redis-server --requirepass ${REDIS_PASSWORD} --maxmemory 512mb --maxmemory-policy allkeys-lru --appendonly yes` and update `REDIS_URL` to `redis://:${REDIS_PASSWORD}@redis:6379`.
2. Bind Redis to internal network only: change `ports: - "6379:6379"` to `ports: - "127.0.0.1:6379:6379"` or remove the `ports:` section entirely (services communicate via Docker network).
3. Similarly, bind the postgres port to localhost: `ports: - "127.0.0.1:${DB_PORT:-5433}:5432"`.
4. Implement off-site backup encryption using `gpg` or `openssl enc` before uploading to remote storage.

### Container Security

#### docker-01 Dockerfile Best Practices — Score: 5/10

**Evidence**:
- `bot/Dockerfile:1` — `FROM node:18-alpine` (pinned to major version tag, not SHA)
- `bot/Dockerfile:9` — `RUN npm ci --production` (production deps only)
- `bot/Dockerfile:14–18` — creates `botuser` group/user, chowns `/app`, uses `USER botuser`
- `bot/Dockerfile:19` — `USER botuser` (non-root, good)
- `bot/Dockerfile` — no `HEALTHCHECK` directive
- No `.dockerignore` file exists in the repository (confirmed by `Glob` search)
- `bot/Dockerfile` — no multi-stage build

**Findings**: Positive: the Dockerfile runs as non-root (`botuser`, uid 1001), uses `npm ci --production` (no dev dependencies in the image), and uses a minimal `alpine` base. Gaps: (1) **No `.dockerignore` file**: the build context (`context: ..` in docker-compose means the entire project root) would include `.env` files, `data/*.json` (admin credentials, transactions), `node_modules/`, and `src.zip`. This means sensitive files are sent to the Docker daemon and could be included in intermediate layers. A `.dockerignore` is critical. (2) **No HEALTHCHECK** in the Dockerfile: Docker relies on the health check defined in `docker-compose.yml` (which does exist: `wget --spider -q http://localhost:4100/bot/health`), but a Dockerfile-level `HEALTHCHECK` is better practice as it works regardless of orchestration method. (3) **Base image pinned to tag `node:18-alpine`**: this is vulnerable to the Node.js 18 EOL (support ended April 2025). The image should be upgraded to `node:20-alpine` or `node:22-alpine` and pinned to a digest. (4) **No multi-stage build**: the production image includes build files (`package*.json`) but not TypeScript sources (the bot is plain JS, so less of a concern), though a multi-stage build could further reduce surface area.

**Remediation**:
1. Create `bot/.dockerignore` (or a root `.dockerignore`) with at minimum: `.env`, `.env.*`, `data/`, `node_modules/`, `*.log`, `dist/`, `coverage/`, `.git/`, `src.zip`.
2. Upgrade base image to `node:20-alpine` (LTS, supported until April 2026) and pin to digest: `FROM node:20-alpine@sha256:<current-digest>`.
3. Add `HEALTHCHECK CMD wget --spider -q http://localhost:4100/bot/health || exit 1` to the Dockerfile.
4. Consider a two-stage build: `FROM node:20-alpine AS build` for dependency install, `FROM node:20-alpine AS runtime` copying only `/app/node_modules` and `/app/bot/src`.

- `bot/docker-compose.yml:60–62` — `bot-api: healthcheck: CMD wget ... /bot/health`

**Findings**: Positive: restart policies are configured on all services. All secrets use `${VARIABLE}` substitution from the environment (no hardcoded credentials in the compose file). The `bot-api` service has a functioning health check. The `pg-backup` service correctly passes `DATABASE_URL` via env var substitution and mounts the backup script read-only. Gaps: (1) **No network segmentation**: all five services (postgres, redis, bot-api, bot-worker, pg-backup) share the default Docker bridge network with no `networks:` configuration. A compromised bot container can directly reach the postgres and redis containers. A dedicated `internal` network for postgres/redis (not exposed to the internet) and a `bot` network for the API would enforce separation. (2) **Redis and postgres port bindings** (already noted in infra-04): `0.0.0.0` binding exposes these to the host network. (3) **No `env_file:` directive**: all environment variables are declared inline in the compose file. Using `env_file: .env` would reduce the `docker-compose.yml` verbosity and avoid duplication, but the current `${VARIABLE}` approach is functionally equivalent and not a security gap per se. (4) **`bot-worker` has no health check**: there is no `healthcheck:` for the worker service — if the BullMQ worker silently crashes, Docker will restart it (`unless-stopped`) but there is no dependency health gate.

**Remediation**:
1. Add Docker networks: define `networks: internal: (internal: true)` and `external:`, attach postgres and redis only to `internal`, and bot-api/bot-worker to both `internal` and `external`.
2. Bind postgres and redis ports to `127.0.0.1` (or remove ports entirely for postgres/redis since only Docker services need them).

#### mon-03 Error Tracking — Score: 4/10

**Evidence**:

- `bot/src/workers/reminder.worker.js:427–432` — BullMQ worker's `failed` and `error` events are logged via `logger.error`

- `bot/src/workers/reminder.worker.js` — BullMQ worker handles `failed` and `error` events on the Worker but `bot/src/worker.js:1–4` has no SIGTERM/SIGINT handler

**Findings**: The bot's monitoring endpoint (`/bot/monitoring/errors`) aggregates failed messages from the database — this is application-level error visibility, not infrastructure error tracking. BullMQ job failures are caught and logged via `reminderWorker.on('failed', ...)` and `reminderWorker.on('error', ...)`. The main website API now has a global error handler (`src/api/app.ts:154–157`). However: (1) **No external error tracking**: if the server is down or the database is unreachable, there is no out-of-band way to know. 2. Consider Sentry free tier for both backend error aggregation and frontend error tracking — add `@sentry/node` and `@sentry/react`.
3. Add SIGTERM/SIGINT handlers to `bot/src/worker.js` that call `reminderWorker.close()` and close the Redis connection before exiting.

### Backup & Recovery

#### backup-01 Database Backups — Score: 7/10

**Evidence**:
- `scripts/pg-backup.sh:1–62` — full backup script with `pg_dump | gzip`, KEEP_DAYS rotation (default 7), timestamped filenames
- `scripts/pg-backup.sh:29` — `set -euo pipefail` (exits on error)
- `scripts/pg-backup.sh:36–39` — fails immediately if `DATABASE_URL` is not set
- `scripts/pg-backup.sh:51–58` — rotation: counts backups, deletes oldest beyond `KEEP_DAYS`
- `bot/docker-compose.yml:90–103` — `pg-backup` service: uses `postgres:15-alpine` image, mounts `./backups:/backups` (local volume, not named volume), runs `while true; do sh /pg-backup.sh; sleep 86400; done`
- `bot/docker-compose.yml:96–98` — `KEEP_DAYS: "7"` in pg-backup environment (7-day retention enforced)
- `bot/DRILL_LOG.md:7–19` — backup drill performed 2026-03-23, PASS: row-count parity verified for visitors/messages
- `bot/BACKUP_RECOVERY.md:5–16` — policy documents 30 daily + 12 monthly retention, off-site required, encryption required
- `bot/BACKUP_RECOVERY.md:70–98` — automated drill script documented (`npm run ops:backup-drill`)

**Findings**: The backup implementation is one of the strongest areas. The script is production-quality: `set -euo pipefail`, fail-fast on missing `DATABASE_URL`, timestamped gzip output, and count-based rotation. The Docker Compose `pg-backup` service runs the script on a 24-hour loop with `restart: unless-stopped`. A backup-restore drill was performed on 2026-03-23 with documented row-count parity verification across 5 tables. Gaps: (1) **7-day rotation only**: the `pg-backup.sh` script retains 7 backups, but `BACKUP_RECOVERY.md` documents a policy of "30 daily + 12 monthly" — there is a gap between the documented policy and the implementation (`KEEP_DAYS=7` in compose). (2) **Local-only storage**: backups are written to `./bot/backups/` (a bind mount to the host). This is on the same server as the database. If the server fails (disk failure, hardware failure), both the database and backups are lost. The policy says "off-site copy: required" but no off-site mechanism is implemented. (3) **No encryption**: backups are stored as unencrypted `.sql.gz` files. The policy states "encryption: at rest and in transit" but the script does not encrypt output. (4) **`pg_dump` format**: uses plain SQL (`pg_dump | gzip`) rather than the custom format (`--format=custom`) which `BACKUP_RECOVERY.md` documents — format inconsistency means restore procedures differ between the script and the documentation.

**Remediation**:
1. Extend `pg-backup.sh` to implement monthly retention: on the first day of each month, copy the daily backup to a `monthly/` subdirectory and retain 12 months.
2. Add off-site transfer: after each backup, upload to an S3-compatible bucket (Cloudflare R2 free tier, Backblaze B2) using `rclone` or `aws s3 cp`.
3. Add GPG encryption: `pg_dump "$DB_URL" | gzip | gpg --encrypt --recipient backup@yourchurch.org > "$BACKUP_FILE.gz.gpg"`.
4. Align the format: use `pg_dump --format=custom` to match the restore command in `BACKUP_RECOVERY.md`.
