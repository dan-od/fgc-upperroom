## Executive Summary

**Overall Weighted Score**: 5.96 / 10  ▲+0.46 from previous (computed)

Three changes in this session materially improve the DevOps posture:

1. **GitHub Actions pinned to SHA** — Both `ci.yml` and `deploy.yml` now use immutable commit SHAs for all four actions: `actions/checkout`, `actions/setup-node`, `actions/upload-artifact`, and `tailscale/github-action`. SHA comments identify the tag. This closes the supply-chain risk that was the primary concern in ci-01.

2. **`permissions: contents: read` added** — Both workflows now declare minimal permissions at job level, preventing the default broad `GITHUB_TOKEN` write scope from being available to workflow steps.

3. **`npm audit --audit-level=high` in CI** — `ci.yml:58–60` now runs `npm audit` before tests. Combined with ESLint (`eslint.config.js` added to project), ci-04 improves significantly. Note: `continue-on-error: true` means audit failures are non-blocking — a compromise that should be reviewed.

4. **Backup encryption** — `scripts/pg-backup.sh` now uses GPG AES-256 when `/run/secrets/backup_key` is present, improving backup-01.

5. **`StrictHostKeyChecking=no` → `accept-new`** — `deploy.yml:92,97,102` changed from `StrictHostKeyChecking=no` (accept any host key, MITM-vulnerable) to `StrictHostKeyChecking=accept-new` (accept first-time hosts, reject changed keys). This meaningfully improves the deploy job's SSH posture.

**Persistent gaps**: Redis still bound to `0.0.0.0:6379` without password, no `.dockerignore`, Node.js 18 base image (EOL April 2025), no network segmentation in Docker Compose, monitoring endpoints still publicly accessible, no Sentry or uptime monitoring, server hardening not documented.

### CI/CD Pipeline Security

#### ci-01 GitHub Actions Security — Score: 8/10 ▲+3

**Evidence**:
- `ci.yml:47` — `actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4` (SHA-pinned)
- `ci.yml:50` — `actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020 # v4` (SHA-pinned)
- `ci.yml:90` — `actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02 # v4` (SHA-pinned)
- `deploy.yml:47` — `actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4` (SHA-pinned)
- `deploy.yml:49` — `actions/setup-node@49933ea5288caeca8642d1e84afbd3f7d6820020 # v4` (SHA-pinned)
- `deploy.yml:78` — `tailscale/github-action@05c58255396c88c609919d571a8b117099c69020 # v2` (SHA-pinned)
- `ci.yml:10` — `permissions: contents: read` (job-level, minimal)
- `deploy.yml:10,63` — `permissions: contents: read` on both jobs (test and build-and-deploy)
- `deploy.yml:92` — `StrictHostKeyChecking=accept-new` (was `StrictHostKeyChecking=no`)
- `deploy.yml:97,102` — same `StrictHostKeyChecking=accept-new` improvement
- `ci.yml` triggers on `pull_request: branches: [main]` — fork PRs cannot access secrets (safe, unchanged)

**Findings**: All four GitHub Actions across both workflows are now SHA-pinned. The SHAs have `# v4` / `# v2` comments for human readability. `permissions: contents: read` is declared at job level in both workflows, replacing the default broad `GITHUB_TOKEN` scope. `StrictHostKeyChecking=accept-new` is a meaningful improvement: it accepts a new host key on first use (correct for CI bootstrap) but rejects changed host keys (detects MITM). This is the right behavior for a deployment workflow that already uses `ssh-keyscan` to populate `known_hosts`.

Remaining minor gap: `workflow_dispatch` on `deploy.yml` allows manual trigger from any authenticated GitHub user with repository write access. A concurrency group (`concurrency: group: deploy-production`) would prevent concurrent deploy races.

**Remediation**:
1. Add `concurrency: { group: deploy-production, cancel-in-progress: false }` to `deploy.yml` to prevent concurrent deployments.
2. Periodically re-check that the pinned SHAs still match the intended version tags (`gh api repos/actions/checkout/git/ref/tags/v4`).

### Backup & Recovery

#### backup-01 Database Backups — Score: 7/10 ▲+1

**Evidence**:
- `scripts/pg-backup.sh:42` — `BACKUP_KEY_FILE="${BACKUP_KEY_FILE:-/run/secrets/backup_key}"`
- `scripts/pg-backup.sh:56-68` — Conditional GPG AES-256 encryption:
  ```bash
  if [ -f "$BACKUP_KEY_FILE" ]; then
    pg_dump "$DB_URL" | gzip | gpg --symmetric --cipher-algo AES256 \
        --passphrase-file "$BACKUP_KEY_FILE" --batch --yes \
        --output "$ENCRYPTED_FILE"
  else
    pg_dump "$DB_URL" | gzip > "$BACKUP_FILE"
    echo "[pg-backup] WARN: No backup key — backup is unencrypted." >&2
  fi
  ```
- `scripts/pg-backup.sh:20-23` — Restore instructions for encrypted backups in header comments
- `scripts/pg-backup.sh:70-72` — Rotation glob: `church_bot_*.sql.gz*` (covers both `.sql.gz` and `.sql.gz.gpg`)
- `bot/docker-compose.yml:92-103` — `pg-backup` service runs the script on a 24-hour loop
- Off-site backup storage still not implemented (documented as policy gap in `bot/BACKUP_RECOVERY.md`)

**Findings**: Backup encryption is now implemented conditionally. When `/run/secrets/backup_key` exists (via Docker secrets mount in production), backups are encrypted with GPG AES-256 symmetric encryption. The fallback to unencrypted with a stderr warning is appropriate for development environments. The rotation logic was updated to handle both `.sql.gz` and `.sql.gz.gpg` patterns. Restore instructions are documented in the script header.

Remaining gap: off-site backup storage is still documented as "required" in `BACKUP_RECOVERY.md` but not implemented in code. Backups are stored in `bot/backups/` within the Docker volume, co-located with the database.

**Remediation**:
1. Implement off-site backup transfer: after creating the backup, use `rclone` or `aws s3 cp` to copy to an off-site storage provider.
2. Add backup integrity verification: run `gpg --verify` or `gunzip --test` after backup creation to ensure the backup file is valid before the old backup is rotated out.
3. Document the backup encryption key storage procedure in `OPERATIONS.md` — who holds the passphrase, where the Docker secret is stored on the production server.
