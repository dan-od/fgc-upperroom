## Executive Summary

**Overall Weighted Score**: 6.05 / 10  ▲+1.55 from previous

This evaluation reflects the compliance remediation work completed in the same day (2026-05-20). Seven major gaps identified in the previous report have been closed:

1. **Privacy policy page** — `src/pages/Privacy/Privacy.jsx` created and accessible at `/privacy`. Comprehensive NDPR-compliant policy covering all 12 data types, third-party processors, retention periods, cross-border transfer disclosure, data subject rights, and opt-out instructions.
2. **Data breach response plan** — `INCIDENT_RESPONSE.md` at project root. Five-step plan (Contain → Assess → Notify NDPC within 72h → Notify individuals → Remediate). NDPC contact (`info@ndpc.gov.ng`) included.
3. **PostgreSQL SSL** — `ssl` option added to all three database pools: `bot/src/db/connection.js`, `attendance/db/connection.js`, and `src/api/giving.db.ts`. Production uses `{ rejectUnauthorized: false }`; dev/test uses `false`.
4. **Message retention purge** — `purge_old_message_data()` PostgreSQL function added to `bot/db/schema.sql`. Purges `messages` and `conversation_feedback` rows older than 90 days. Ready to be scheduled via `pg_cron` or application cron.
5. **LLM PII minimization** — `message-generator.service.js` now extracts `firstName` before building prompts. Full names no longer sent to Vertex AI, OpenAI, or Gemini. Phone numbers and emails were already excluded.
6. **Backup encryption** — `scripts/pg-backup.sh` now encrypts backups with GPG AES-256 when `/run/secrets/backup_key` is present. Falls back to unencrypted with a stderr warning.
7. **Data subject rights contact** — Published in the privacy policy: `info@fgcupperroom.org`. Covers the right to access, rectification, erasure, and data portability.

**Remaining gaps**: WhatsApp sign-up modal still lacks an explicit consent checkbox (consent-01 partial); prayer request visibility is not restricted to pastoral staff (access-01); no formal DPIA (ndpr-02); RBAC giving data masking only on PostgreSQL path, not JSON store path (access-01 partial).

#### min-02 Data Retention Policy — Score: 7/10 ▲+3

**Evidence**:
- `bot/db/schema.sql` — NEW function at end of file:
  ```sql
  CREATE OR REPLACE FUNCTION purge_old_message_data() RETURNS void
  LANGUAGE plpgsql AS $
  BEGIN
    DELETE FROM messages
    WHERE created_at < now() - INTERVAL '90 days';
  
    DELETE FROM conversation_feedback
    WHERE created_at < now() - INTERVAL '90 days';
  END;
  $;
  ```
- `src/pages/Privacy/Privacy.jsx` — privacy policy documents retention periods:
  - Messages: 90 days
  - Attendance: 2 years
  - Prayer requests: 30 days (unless saved by submitter)
  - Visitor/member data: duration of membership + 2 years
  - Giving transactions: 7 years (financial record requirement)
- No scheduled call to `purge_old_message_data()` confirmed in codebase (must be wired to `pg_cron` or app cron)

**Findings**: A 90-day purge function now exists for the two most privacy-sensitive tables (`messages` contains full WhatsApp message text; `conversation_feedback` contains feedback text with phone numbers). The retention period is documented in the privacy policy, satisfying NDPR's requirement for a defined retention schedule. The main gap: the function must still be scheduled. Without a `pg_cron` job or a node-cron call, `purge_old_message_data()` exists but does not run automatically.

**Remaining remediation**:
1. Schedule `purge_old_message_data()` via pg_cron: `SELECT cron.schedule('purge-messages', '0 3 * * *', $$SELECT purge_old_message_data()$$);` in `bot/db/schema.sql`.
2. Alternatively, call it from the existing `node-cron` job in `bot/src/workers/` (weekly or daily at low-traffic time).
3. Add a similar purge for `prayer_requests` older than 30 days and `event_rsvps` older than 1 year (documented in policy but no function exists).

#### sec-02 Data at Rest — Score: 6/10 ▲+3

**Evidence**:
- `scripts/pg-backup.sh:12` — `BACKUP_KEY_FILE="${BACKUP_KEY_FILE:-/run/secrets/backup_key}"`
- `scripts/pg-backup.sh:56-68` — Conditional encryption:
  ```bash
  if [ -f "$BACKUP_KEY_FILE" ]; then
    ENCRYPTED_FILE="${BACKUP_FILE}.gpg"
    pg_dump "$DB_URL" | gzip | gpg --symmetric --cipher-algo AES256 \
        --passphrase-file "$BACKUP_KEY_FILE" --batch --yes \
        --output "$ENCRYPTED_FILE"
    echo "[pg-backup] Saved (encrypted): $ENCRYPTED_FILE"
  else
    pg_dump "$DB_URL" | gzip > "$BACKUP_FILE"
    echo "[pg-backup] WARN: No backup key — backup is unencrypted." >&2
  fi
  ```
- `scripts/pg-backup.sh:20-23` — Restore instructions for encrypted backups documented in header
- `scripts/pg-backup.sh:70-72` — Rotation glob updated: `church_bot_*.sql.gz*` (covers both `.sql.gz` and `.sql.gz.gpg`)
- `data/admin-users.json` — still plain filesystem JSON (TOTP secrets, password hashes); no encryption
- `data/*.json` flat files — no file-level encryption

**Findings**: PostgreSQL backups now have GPG AES-256 encryption when the passphrase file exists at `/run/secrets/backup_key`. The fallback to unencrypted with a warning is appropriate for development. The admin JSON flat files (`admin-users.json`, `admin-sessions.json`) containing TOTP secrets and password hashes remain plain JSON on disk, relying on OS-level filesystem permissions. This is an acceptable risk at church scale but ideally should be replaced with PostgreSQL storage long-term.
