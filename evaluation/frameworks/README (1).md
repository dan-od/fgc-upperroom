# FGC Upper Room — Evaluation Framework System

## Overview

This system evaluates the FGC Upper Room codebase against structured security, quality, and compliance frameworks. Inspired by the "createFramework + analyzeFramework" pattern — frameworks define what to check, evaluations score the codebase against them, and results track progress over time.

## Directory Structure

```
evaluation/
├── README.md                  ← You are here
├── frameworks/                ← JSON evaluation criteria (the "what to check")
│   ├── 01-security.json       ← Authentication, secrets, input validation, crypto
│   ├── 02-code-quality.json   ← Structure, naming, duplication, testing
│   ├── 03-api-security.json   ← Endpoint inventory, WhatsApp, attendance, Paystack readiness
│   ├── 04-compliance.json     ← NDPR, data privacy, consent, retention
│   ├── 05-frontend.json       ← Performance, a11y, SEO, responsive design
│   └── 06-devops.json         ← CI/CD, infrastructure, monitoring, backups
└── results/                   ← Evaluation reports (generated by running analysis)
    └── (empty — results go here)
```

## How to Run an Evaluation

### Quick Run (Single Framework)

```
Prompt to Claude Code:

"Read evaluation/frameworks/01-security.json and evaluate the current codebase 
against every criterion. Score each 1-10 with file:line evidence. Output the 
report to evaluation/results/security-eval-{timestamp}.md following the report 
format specified in the framework."
```

### Full Run (All Frameworks)

```
Prompt to Claude Code:

"Read all JSON files in evaluation/frameworks/ and run a complete evaluation 
of the codebase. For each framework, score every criterion 1-10 with evidence. 
Generate individual reports in evaluation/results/ plus a summary dashboard."
```

### Re-Evaluation (Track Progress)

```
Prompt to Claude Code:

"Read evaluation/frameworks/01-security.json and re-evaluate the codebase. 
Compare results against the most recent report in evaluation/results/ that 
starts with 'security-eval-'. Show score changes per criterion and overall 
progress."
```

## Scoring System

Each criterion is scored 1-10:

| Score | Rating    | Meaning                                                |
|-------|-----------|--------------------------------------------------------|
| 1-2   | Critical  | Actively exploitable or fundamentally broken           |
| 3-4   | Poor      | Major gaps. Missing fundamental controls               |
| 5-6   | Fair      | Some controls exist but significant gaps remain        |
| 7-8   | Good      | Solid implementation with minor improvements needed    |
| 9-10  | Excellent | Industry best practices implemented and verified       |

Categories have weights (1.0 = standard, 1.5 = high priority). The overall score is a weighted average.

## Report Format

Each report includes:

1. **Executive Summary** — Overall weighted score, critical finding count, top 3 priorities
2. **Category Scores** — Table with category name, raw score, weight, weighted score
3. **Detailed Findings** — Per criterion: score, evidence (file paths, line numbers, code snippets), specific remediation steps
4. **Action Items** — Ordered by severity, with estimated effort (quick fix / medium / large refactor)
5. **Progress Tracking** — Comparison with previous evaluation (if exists)

## Framework Details

### 01 — Security (Weight: Highest)
**30 criteria** across 9 categories: authentication, authorization, secrets, input validation, cryptography, headers, error handling, dependencies, WhatsApp-specific security.

Key focus areas specific to FGC:
- Admin auth system (RBAC with super_admin/editor/reviewer)
- WhatsApp Bot webhook verification and message handling
- VITE_ env var exposure (Phase 1 removed — verify clean)
- LLM prompt injection (Vertex AI/OpenAI/Gemini cascading providers)
- JSON file data store security (data/*.json files still in use)
- Giving notification endpoint (/bot/api/giving/notify) security

### 02 — Code Quality (Weight: High)
**17 criteria** across 7 categories: project structure, naming, duplication, error handling, React patterns, documentation, testing.

Key focus areas:
- Monolithic server.ts (check current size after 5 phases of changes)
- Dead code from AI-generated features
- maskPhone() duplication across 3+ files
- Existing test suite (10 unit, 9 integration, E2E, a11y, perf, security smoke tests)
- JSON file data stores still in use alongside PostgreSQL

### 03 — API Security (Weight: High)
**16 criteria** across 7 categories: endpoint inventory, WhatsApp API, attendance API, admin API, public API, Paystack (live), LLM API security.

Key focus areas:
- Complete endpoint map with auth classification
- Unauthenticated write endpoints (previously found)
- Paystack is live — evaluate HMAC-SHA512 webhook validation, transaction state machine, bot notification bridge
- /bot/api/giving/notify internal endpoint security
- Rate limiting consistency across all public endpoints

### 04 — Compliance (Weight: Medium-High)
**15 criteria** across 6 categories: consent, data minimization, access control, technical protection, transparency, NDPR-specific.

Key focus areas:
- NDPR (Nigeria Data Protection Regulation) compliance
- WhatsApp opt-in/opt-out consent flows
- Church member data privacy (phone numbers, prayer requests, giving records — now live in PostgreSQL)
- LLM data leakage: member PII sent to US-based AI providers (cross-border transfer concern)
- Data retention policies
- Privacy policy page existence

### 05 — Frontend (Weight: Medium)
**16 criteria** across 5 categories: performance, accessibility, SEO, responsive design, UX.

Key focus areas:
- Mobile performance for Nigerian users on 3G/4G
- Bundle size and code splitting (including giving dashboard lazy loading)
- PWA readiness (manifest.json, service worker, offline capability)
- i18n readiness (src/i18n/ directory exists — complete, half-done, or dead code?)
- Accessibility (semantic HTML, keyboard nav, screen readers)
- Offline/low-connectivity resilience

### 06 — DevOps (Weight: Medium)
**16 criteria** across 5 categories: CI/CD pipeline, infrastructure, containers, monitoring, backups.

Key focus areas:
- GitHub Actions workflow security
- Environment parity check system (scripts/check-env-parity.mjs)
- Proxmox server hardening
- Docker configuration (including pg-backup service)
- PostgreSQL backup automation (scripts/pg-backup.sh — verify it works)
- Health checks and uptime monitoring
- Logging maturity gap between bot service (structured JSON) and website API (basic request logging)

## Tips for Best Results

1. **Run one framework at a time** for thorough analysis — Claude Code can focus more deeply
2. **Start with Security (#01)** — it's the highest risk
3. **After fixing issues, re-run** the same framework to track improvement
4. **N/A scores** are fine — Paystack isn't implemented yet, so score those criteria as readiness assessments
5. **Evidence matters** — every score should cite specific files and line numbers
6. **Known issues** in the frameworks reference findings from a March 2026 audit — check if they're fixed

## Adding Custom Frameworks

To add a new evaluation framework, create a JSON file following the same schema:

```json
{
  "framework": {
    "id": "unique-id",
    "name": "Display Name",
    "version": "1.0.0",
    "created": "YYYY-MM-DD",
    "description": "What this framework evaluates",
    "scoring": { ... }
  },
  "categories": [
    {
      "id": "category-id",
      "name": "Category Name",
      "weight": 1.0,
      "criteria": [
        {
          "id": "criterion-id",
          "name": "Criterion Name",
          "what_to_check": ["list", "of", "things", "to", "verify"],
          "known_issues": ["optional: previously identified problems"],
          "remediation": "How to fix issues found"
        }
      ]
    }
  ],
  "evaluation_instructions": { ... }
}
```
